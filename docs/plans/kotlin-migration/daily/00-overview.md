## 모든 팀원이 지킬 작업 순서

1. **현재 동작부터 확인합니다.** 기존 테스트와 Java 호출부를 찾고 부족한 사례를 보강합니다. P0 세부 항목은 [테스트 준비](../01-test-baseline.md)·[금전/동시 요청](../02-money-and-concurrency.md)·[API 확인](../03-api-contract.md)을 봅니다.
2. **작게 나눠 옮깁니다.** 한 PR에는 정책 하나나 서로 밀접한 파일 묶음을 담습니다. 같은 클래스의 Java 원본 삭제와 Kotlin 추가를 함께 반영하고 Java 호출부도 맞춥니다.
3. **선행 작업을 기다립니다.** 빌드 설정 PR이 합쳐진 뒤 Kotlin 전환을 시작합니다. 필요한 P0가 남으면 DB·핵심 서비스 전환보다 테스트를 먼저 마칩니다. 그래서 `BaseTimeEntity`는 일요일, DB를 쓰는 중복 요청 처리는 일~월요일, PG 설정은 토요일에 배치했습니다.
4. **테스트하고 전체 빌드를 확인합니다.** 관련 테스트 후 각 전환 PR에서 아래 전체 빌드를 실행합니다. API·공유 데이터 형식에 영향이 있으면 프론트 검사도 합니다.
5. **결과와 남은 일을 남깁니다.** 완료 파일/PR, 테스트 결과, 못 확인한 항목, 다음 날 필요한 내용을 공유합니다. [공통 완료 기준](../README.md#완료-기준)은 빌드 성공·기존 동작 유지·중 이상 문제 없음입니다. 필요한 확인을 못 했다면 ‘확인 필요’로 남깁니다.

## 빌드·테스트 명령

JDK 21과 Docker를 준비합니다. 아래 `cd`는 각각 저장소 루트에서 시작하는 예시입니다. 백엔드는 특정 테스트만 통과한 결과와 구분해 **전체 테스트를 포함한 빌드**를 확인합니다.

```bash
cd backend
./gradlew clean build
```

DTO·API·공유 데이터 형식에 영향이 있으면 프론트 검사도 실행합니다. 백엔드만 바뀐 PR에는 프론트 CI가 자동 실행되지 않을 수 있습니다.

```bash
cd frontend
node --test tests/*.cjs
npx tsc --noEmit
```

프론트 코드도 수정했다면 `npm run lint`·`npm run build`를 추가합니다. 메일/Kafka 환경 변수 정리는 [기존 실행 조건](../01-test-baseline.md)을 따릅니다.

결과에는 날짜·커밋·명령·종료 코드와 실제 테스트 보고서(XML)의 실행/실패/오류/스킵 수를 남깁니다. 팀이 공유할 실행 결과는 [테스트 결과](../../../testing/test-results.md)에, 변경 내용과 리뷰는 해당 PR에 기록합니다. 가짜 PG/메일·Kafka OFF 테스트와 실제 외부 연결 결과를 구분합니다.

- 작업은 현재 **3차 저장소**에서 진행합니다. 2차 저장소는 Java 원본 비교용입니다([상세 전환 계획](../07-code-migration.md)).
- 기존 단계와 대응: 목요일 `step-0`·`step-1`, 금요일 `step-2`, 토요일 `step-3`, 일~월요일 `step-4`, 화요일 `step-5` 후 조건을 갖추면 `step-6`입니다.
- 최초 작성 시점은 운영 Java 293개·테스트 Java 148개·Kotlin 0개였습니다. 2026-10-20 `d1a15ec`의 135개 스위트·1,048건 통과는 과거 비교 자료입니다. 앞으로 바꾼 코드의 결과는 새로 확인합니다.
- 시작 시 현재 커밋·CI·Flyway 목록을 다시 확인합니다. 기존 DB 변경 파일과 API/메시지 형식을 유지하고, 데이터나 외부 규칙 변경은 별도 작업으로 나눕니다. 기존 규칙을 유지한 PR은 해당 PR 단위로 되돌릴 수 있게 만듭니다.
- CI 배포는 `DEPLOY_ENABLED` 조건이 켜져야 실행됩니다. 빌드 통과·JAR 생성·실제 서버 시작과 HTTP 응답은 각각 확인한 만큼만 기록합니다.
