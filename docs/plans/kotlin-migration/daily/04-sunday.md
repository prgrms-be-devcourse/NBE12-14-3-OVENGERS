# 4. 일요일(10/25) — DB에 저장하고 읽는 코드 옮기기

> 기존 단계: step-4 전반 · 앞으로 할 일을 정리한 계획입니다.
> [0. 팀 공통 안내](00-overview.md) · 이전: [3번 계획](03-saturday.md) · 다음: [5번 계획](05-monday.md)

## 오늘의 목표

**공통 엔티티와 비교적 단순한 DB 저장·조회 코드부터 옮깁니다. 실제 DB에 저장한 값을 다시 읽어도 데이터와 관계가 같아야 합니다.**

## 시작 전에 확인할 것

해당 기능의 P0와 DB 테스트 환경이 준비되어야 합니다. 공통 부모 클래스 `BaseTimeEntity`를 먼저 바꿔도 상속 엔티티가 정상 동작하는지 확인합니다. 실패하면 이를 사용하는 엔티티 전환은 기다립니다.

## 오늘 완료했다고 말하려면

- 실제 MySQL에 저장한 뒤 다시 읽어 값·null 허용 여부·연관 데이터·생성/수정 시각을 확인합니다.
- 문의 수정 제한, 로그인 실패 기록, 대기열 중복 방지와 동시 수정 처리가 기존대로 동작해야 합니다.
- 기존 DB 구조와 Flyway 변경 파일을 유지하고 관련 DB 테스트를 실행합니다. DB 테스트를 못 했다면 ‘확인 필요’로 남깁니다.
- PR마다 [공통 안내의 전체 빌드·필요한 프론트 검사](00-overview.md)를 실행합니다.

## 구현할 때 참고

- 공간·회원·인증 세션/증표·예약/슬롯·충전 주문·출입 토큰/로그·크레딧 내역의 핵심 엔티티 전환은 화요일입니다. 오늘의 저장소가 Java 엔티티를 사용해도 함께 빌드되어야 합니다.
- 김재철: `BaseTimeEntity`, `AuditLog`·Repository, `SpaceRankingSnapshot`과 통계 JDBC/Repository. 순매출 long·건수 int, `[from,to)` 기간을 유지합니다.
- 백한비: `IdempotencyKey`·Repository, `ReservationStatusHistory`·Repository, 원장/잔액 Repository의 조건부 UPDATE 영향 행 수와 자동 flush/clear 설정.
- 이태호: `OutboxEvent`, `Notification`, `WaitlistEntry`·Repository. `active = NULL/1`, `@DynamicUpdate`, 저장 타입·인덱스를 유지합니다.
- 천종원: `Inquiry`·Repository·관련 서비스, `JdbcLoginAttemptStore`. 실패 기록을 별도로 확정하는 `REQUIRES_NEW`와 `FOR UPDATE`를 유지합니다.
- [JPA·프록시 계획](../06-jpa-and-proxies.md)에 따라 일반 `class`와 기존 동등성을 유지합니다. 저장→flush→clear→재조회, LAZY·Auditing·nullable, Java 생성자/getter/정적 팩터리, `javap`의 open/no-arg와 Flyway checksum을 확인합니다.
- `./gradlew test --tests '*RepositoryTest' --tests '*IntegrationTest'` 후 필요한 JDBC·동시성 테스트와 전체 빌드를 실행합니다. 이름에 잡히지 않는 클래스는 따로 지정합니다.
