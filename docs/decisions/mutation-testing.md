# AI가 쓴 테스트의 약점을 뮤테이션 테스트(PIT)로 확인한다

> **상태:** 채택 (2026-10-26, 사용자 확인). 0~6단계와 후속 #154를 모두 마쳤다(2026-10-26). 최종 결과는 §5 "최종 결과 요약"에 있다. 범위·순서는 [plans/mutation-testing](../plans/mutation-testing/00-mutation-testing-plan.md)에 있고 여기에 복사하지 않는다.

## 한 줄 요약

AI가 작성하거나 Kotlin 전환 중 옮긴 테스트가 "틀렸는데 통과"하거나 "빠져 있는" 경우를 찾기 위해, 프로덕션 코드를 일부러 바꿔 보고(뮤턴트) 테스트가 실패하는지 보는 뮤테이션 테스트 도구 PIT(Pitest)를 핵심 도메인 로직에 한정해 도입한다.

## 1. 문제와 배경

- 2차 프로젝트 보완·기능 추가 과정에서 테스트가 많이 늘었고, 3차에서 Java → Kotlin 마이그레이션을 거쳤다. 이 과정에서 AI가 테스트를 작성·변환했다. 외부 피드백으로 "AI 테스트가 틀렸는데 통과하거나 누락된 테스트가 있을 수 있으니 확인이 필요하다"는 지적을 받았다.
- 테스트 수와 라인 커버리지는 이 문제를 잡지 못한다. 단언(assert)이 약하거나 경계값이 빠져도 줄은 실행되고 테스트 수는 그대로다. [`kotlin-test-guardrails.md`](kotlin-test-guardrails.md)의 테스트 수 하한도 같은 한계를 인정한다(§6: "테스트 수가 같아도 단언이 약해진 경우는 잡지 못한다").
- 이미 수동 뮤테이션을 한 적이 있다. 전환 중 `ReservationTimePolicy` 검증에서 나노초 검사를 일부러 빼 보고 새 테스트 2개가 실패하는 것을 확인했다([`step-1.md`](../lab/notes/kotlin-thursday-policies/step-1.md) 45행). 이를 자동화·일반화하는 것이 이번 결정이다.
- 제약: 일정(3차 마지막 주), 테스트 중 통합 테스트는 Testcontainers(MySQL)를 써서 느리다. Java 테스트(약 128개 파일)와 Kotlin 테스트(약 38개 파일)가 섞여 있다. `AGENTS.md` 규칙상 구현은 한 단계씩, 결정 문서가 먼저다.

## 2. 선택과 이유

- 선택한 방법: Gradle 플러그인 PIT(Pitest)를 추가하고, **단위 테스트로 빠르게 돌릴 수 있는 핵심 도메인 로직**에만 적용한다. 살아남은 뮤턴트를 읽고 테스트를 보강한다.
- 이유:
  - 도구가 기계적으로 코드를 바꾸므로 "AI가 쓴 코드와 테스트를 AI가 다시 검토"하는 순환을 피한다. 사람이 살아남은 뮤턴트를 판단한다.
  - 1차 대상 정책 클래스(`ReservationTimePolicy`, `ReservationRefundPolicy`)는 이미 스프링 없는 단위 테스트가 있어 실행이 빠르다.
  - 의존성은 Gradle 플러그인 한 개 수준이고 운영 코드에 영향이 없다.
- 적용 대상 우선순위와 제외 대상은 plan §2에 둔다.
- 사용자 결정 (2026-10-26):
  - 목표: 포트폴리오 서사가 우선이다. 품질 게이트(점수 미달 시 CI 차단)는 목표가 아니다.
  - 범위: 본인(이태호) 담당 도메인에서 정책 클래스로 시작해 `PricingService`, 상태 전이(`Reservation`, `ChargeOrder`)까지 넓히고, 이후 다른 팀원 담당 클래스(`DoorAccessTimePolicy`, `SpaceOperatingHoursPolicy`, `CreditService`)까지 포함한다.
  - 진행 방식: 한 사람이 PIT 설정·실행·측정·테스트 추가를 모두 맡아 설정과 기준을 하나로 유지한다. 다른 팀원 담당 클래스의 테스트는 새 파일로 추가하고, PR은 해당 담당자의 리뷰를 받는다.
  - 실행: CI에 넣지 않고 수동으로 실행한다. 실행 시간을 측정한 뒤 편입 여부를 다시 본다.
  - 성과 기록: 점수 목표는 두지 않는다. 전/후 점수는 참고로 적고, 발견한 구멍 N개, 추가한 테스트 M개, 대표 사례 3개로 기록한다. 대표 사례는 새로 추가한 테스트뿐 아니라 기존 테스트가 뮤턴트를 잘 잡은 경우에서도 고를 수 있다.

## 3. 기각한 대안과 이유

| 대안 | 장점 | 기각한 이유 |
| --- | --- | --- |
| 라인·분기 커버리지(JaCoCo)만 사용 | 설정이 쉽고 실행이 빠르다 | 코드가 실행됐는지만 보고 단언이 맞는지는 모른다. 지적받은 "틀렸는데 통과"를 못 잡는다. |
| 사람이 테스트를 전수 코드 리뷰 | 도구가 필요 없다 | 테스트 수천 건을 읽는 비용이 크고 놓치기 쉽다. 이미 AI 작성분을 사람이 보는 것이 병목이다. |
| 수동 뮤테이션(코드를 직접 바꿔 보기)만 계속 | 이미 해 본 방식이고 도구 비용이 없다 | 반복·재현이 어렵고 범위가 사람 주의에 달려 있다. 첫 시도로는 유효했으나 확장성이 없다. |
| LLM에게 테스트를 다시 검토시키기 | 설정 없이 바로 가능 | 같은 계열의 오류를 반복할 수 있고 검증 결과가 재현되지 않는다. 보조 수단으로만 쓴다. |
| 전체 코드베이스에 적용 | 한눈에 점수가 나온다 | Controller·Repository·DTO·설정은 로직이 적고 통합 테스트 실행이 느려 시간 대비 얻는 것이 적다. 노이즈 뮤턴트도 늘어난다. |

## 4. Trade-off

| 얻는 것 | 잃는 것(비용·위험) | 완화책 |
| --- | --- | --- |
| 테스트가 실제로 버그를 잡는지 객관적 근거 | 실행 시간 증가(뮤턴트마다 테스트 재실행) | 대상 클래스·테스트를 한정, CI 상시 실행은 보류 |
| 누락된 경계값·약한 단언 발견 | Kotlin 컴파일러 생성 코드(null 체크, `when`)에서 의미 없는 뮤턴트 | 점수보다 살아남은 뮤턴트를 개별로 읽고 동치 뮤턴트는 사유를 적어 제외 |
| "AI 코드를 사람이 검증했다"는 재현 가능한 증거 | 점수 숫자만 쫓으면 형식적 테스트가 늘 수 있음 | 목표 점수 대신 "발견한 구멍과 보강한 테스트" 기록을 성과로 삼는다 |

## 5. 검증 (검증 계획, 구현 후 "검증 결과"로 바꾼다)

- 대상 클래스별로 도입 전 점수와 살아남은 뮤턴트 목록을 기록한다.
- 살아남은 뮤턴트를 "테스트 구멍 / 동치 뮤턴트 / 대상 아님"으로 분류하고, 구멍은 테스트를 추가해 죽인다(테스트 먼저 작성·실패 확인 원칙 적용).
- 도입 후 점수(참고)와 발견한 구멍 N개, 추가한 테스트 M개, 대표 사례 3개(뮤턴트, 테스트, 결과)를 이 절에 적는다. 대표 사례는 기존 테스트에서 골라도 된다.
- 실행 시간을 기록해 CI 편입 가능 여부를 판단한다.
- 점수 100% 달성은 목표가 아니다.

### 최종 결과 요약 (6단계, 2026-10-26)

> 아래 수치는 모두 Claude가 구현과 다른 세션에서 직접 재실행해 확인한 것이다. 단계별 상세 기록은 이 요약 아래에 남겨 둔다.

**구멍을 세는 기준:** 기존 테스트를 모두 통과한 서로 다른 뮤턴트(또는 수동 변조) 1건을 구멍 1개로 센다. `CreditServiceImpl`의 장부-예약 연결(H3)은 PIT 뮤턴트 1건이고 차감·환불·위약금 경로별 수동 변조 3건으로 확인했지만 1개로 센다.

| 단계 | 대상 | 방법 | 구멍 | 추가한 테스트 | 직접 죽인 테스트 | 경계 고정용 |
| --- | --- | --- | ---: | ---: | ---: | ---: |
| 1 | 정책 2개 | PIT 기본 변이 세트 | 0 | 0 | 0 | 0 |
| 2 | 정책 2개 | PIT `STRONGER` | 1 | 4 | 1 | 3 |
| 3 | `PricingService` | PIT | 0 | 0 | 0 | 0 |
| 4 | `ChargeOrder` | PIT | 1 | 1 | 1 | 0 |
| 4 | 예약 조건부 UPDATE 10개 | 수동 변조 20건 | 6 | 8 | 7 | 1 |
| #154 | `ChargeOrder` 전이·쿼리 | 수동 변조 20건 | 5 | 2 | 2 | 0 |
| 5 | `DoorAccessTimePolicy`, `SpaceOperatingHoursPolicy`, `CreditServiceImpl` | PIT 측정 후 `CreditServiceImpl`만 보강 | 3 | 6 | 5 | 1 |
| 합계 | | | **16** | **21** | **16** | **5** |

**점수는 참고만 한다.** 정책 2개와 `PricingService`는 보강 후 뮤턴트가 100% 잡혔고(정책 2개 39개 중 39개), `CreditServiceImpl`은 36개 중 28개에서 31개로 늘었다. 남은 뮤턴트는 위험이 낮은 null 검사와 Kotlin이 생성한 코드다. 점수 목표는 처음부터 두지 않았다.

**확정한 대표 사례 3개**

| # | 사례 | 기존 테스트가 못 잡은 이유 | 추가한 테스트와 결과 |
| --- | --- | --- | --- |
| 1 | 예약 종료 시각이 운영 마감을 넘어도 통과(`ReservationTimePolicy`) | 기존 테스트는 "시작이 오픈 전"만 확인했다. 라인 커버리지는 이미 100%여서 줄이 실행되기만 하면 통과했다 | 종료가 마감을 넘는 경우를 확인하는 테스트 추가. 검사를 지우면 실패한다 |
| 2 | 노쇼·자동 체크아웃·HELD 취소 쿼리의 경계와 상태 가드(`ReservationRepository`) | 기존 서비스 테스트는 Repository를 mock으로 대체해 **쿼리(JPQL)를 실행하지 않았다.** PIT도 쿼리 문자열은 변조하지 못한다 | 실제 MySQL로 정각·1초 전·1초 후를 고정하는 통합 테스트 추가. 수동 변조 6건 모두 실패한다 |
| 3 | 환불·차감·위약금 장부가 어느 예약의 거래인지 연결되지 않아도 통과(`CreditServiceImpl`) | 기존 테스트는 장부의 금액·종류·잔액만 단언하고 예약 연결은 단언하지 않았다 | 세 경로에서 같은 예약이 연결됐는지 확인하는 테스트 추가. 변조 3건 모두 실패한다 |

사례 3은 금액이 틀어지는 문제가 아니다. 금액과 거래 종류는 기존 테스트가 이미 확인하고 있었고, 빠져 있던 것은 "이 거래가 어느 예약에서 생겼는지"라는 추적 정보다. 장부 추적성 구멍으로 쓴다.

**구멍이 없거나 작았던 곳 (이것도 결과다)**
- `DoorAccessTimePolicy`: 뮤턴트 16개 전부 잡힘.
- `PricingService`: 4개 전부 잡힘.
- 돈이 오가는 핵심(주문 상태 `PAID` 전이, 잔액 증가, 원장 기록)은 기존 테스트가 이미 탄탄했다. `ChargeOrder`에서 찾은 구멍 5개는 보조 메타데이터(실패코드·복구 예약·갱신 시각) 정리였다.
- `SpaceOperatingHoursPolicy`: 의미 있는 구멍 후보 1건(`date`가 null이면 NPE)이 있었지만 컨트롤러가 `date`를 필수로 받아 실제 위험이 낮아 조치하지 않았다.

**검증 과정에서 걸러낸 것들 (AI 협업 검증 체계의 증거)**
- 구현자(Codex)가 "돈 관련 대표 사례"라고 쓴 `ChargeOrder` 구멍을 검증자(Claude)가 실제 영향을 따져 과장이라고 정정했다.
- Gradle이 테스트를 `up-to-date`로 건너뛰어 5초 만에 끝난 실행을 증거로 쓰지 않고 `cleanTest`로 다시 돌렸다.
- 단언이 아니라 쿼리 파라미터 미사용으로 컨텍스트가 깨져 "잡힌" 약한 kill 4건을 따로 구분했다.
- 계획에 대상으로 적은 `CreditService`가 인터페이스여서 `CreditServiceImpl`로 정정했다.
- 구현자 보고서의 "기존 테스트가 잡았다/못 잡았다" 주장을 변조를 직접 다시 적용해 확인했다: 4단계(잡힘 14건 재변조, 구멍 6건 재현), #154(20건 전부 재현), 5단계(5건 재현).

**CI 편입 판단 (실행 시간 기준)**

| 항목 | 측정값 |
| --- | --- |
| `./gradlew pitest` (단위 테스트만, Gradle 기동 포함) | 약 22초~43초 |
| 통합 테스트까지 포함한 PIT(`Reservation*` 대상) | 7분 17초 |
| 전체 `./gradlew cleanTest test` | 약 9분 23초~10분 |

PIT를 단위 테스트로 한정하면 가볍지만, 이 작업의 목적은 점수 게이트가 아니라 "구멍을 찾아 보강하는 것"이었다. 점수 목표가 없어서 CI가 막을 기준도 없고, 대상 클래스 목록을 CI가 관리하면 팀 PR마다 설정 충돌이 생긴다. 그래서 수동 실행(`./gradlew pitest`)을 유지한다. 새 테스트 클래스를 만들 때는 `build.gradle`의 `targetTests`에 추가해야 PIT가 반영한다(5단계에서 `CreditServiceImplMutationTest`가 빠져 28 killed로 되돌아 보이는 문제를 발견해 추가함).

## 6. 한계와 재검토 조건

- 뮤테이션 테스트는 단위 수준의 단언 품질을 본다. 동시성·멱등성 같은 경합 문제는 뮤턴트로 잡히지 않으므로 기존 통합 테스트가 계속 필요하다.
- 동치 뮤턴트(동작이 안 바뀌는 변경)는 사람이 판단해야 한다.
- 재검토 조건: 실행 시간이 허용 범위를 넘거나, Kotlin 노이즈로 신호가 묻히거나, 대상 확장 후에도 새 구멍이 나오지 않으면 범위를 줄이거나 도구를 바꾼다. (이번에는 모두 해당하지 않았다. 확장할수록 구멍이 줄었고 마지막 클래스 3개에서는 의미 있는 구멍이 1개 클래스에만 나왔다.)
- 오픈소스 PIT는 **필드 대입과 쿼리(JPQL) 문자열을 변조하지 못한다.** 이 영역은 수동 변조로 보완했지만 재현성이 낮고 사람 시간이 든다. 대입 변조가 필요하면 Arcmutate 같은 상용 확장을 검토할 수 있다.
- 구멍을 센 기준(기존 테스트를 통과한 서로 다른 뮤턴트·변조 1건)은 단순하지만 구멍의 심각도를 반영하지 않는다. 사례 3개의 구멍은 의미가 크고, `ChargeOrder`의 보조 메타데이터 5개는 상대적으로 작다. 개수 대신 대표 사례로 설명한다.
- 수동 변조 중 `SET status` 계열 4건은 컨텍스트 로딩 실패로 잡혀 단언이 잡았다는 증거가 약하다.
- 후보 조회 쿼리 3개(`findExpiredHoldIds` 등)와 `ReservationBatchProcessor`의 `now - 15분` 계산은 경계에서 변조하지 않았다. UPDATE가 조건을 다시 검사해 위험은 낮다.
- `Reservation` 엔티티의 호출되지 않는 전이 메서드 7개는 유지하기로 했다(#155). 규칙이 엔티티와 쿼리에 중복돼 있어 한쪽만 고치면 어긋날 수 있다. 팀이 이 메서드를 쓰거나 삭제하기로 하면 이 문서를 갱신한다.
- 일부 구멍 후보(H4 null ID, `date` null NPE)는 위험이 낮아 다루지 않았다.

## 면접·발표용 정리 (구현 후)

- **30초 설명:** AI가 쓰거나 옮긴 테스트가 "통과하는데 믿을 수 있나"를 확인하려고 뮤테이션 테스트 도구(PIT)를 도입했습니다. 도구가 운영 코드를 일부러 망가뜨려 보고, 그래도 테스트가 통과하면 그 부분을 확인하는 테스트가 빠져 있다는 뜻입니다. 예약·크레딧 핵심 로직을 측정해 구멍 16개를 찾고 테스트 21개를 보강했습니다. 라인 커버리지가 100%여도 마감 시각 검사가 비어 있었고, 도구가 못 보는 쿼리 속 규칙은 직접 코드를 한 줄씩 바꿔 가며 검증했습니다. 돈이 오가는 핵심은 이미 튼튼했고, 구현은 Codex가 하고 저는 별도 세션에서 수치를 직접 재실행해 과장과 오류를 걸러냈습니다.
- **예상 질문과 답:**
  - Q. 왜 커버리지 대신 뮤테이션 테스트를 썼나요?
    A. 커버리지는 줄이 실행됐는지만 봅니다. 마감 시각 검사 사례는 라인 커버리지 100%인데도 그 검사를 지워도 모든 테스트가 통과했습니다. 뮤테이션 테스트는 "테스트가 틀린 코드를 실제로 잡는가"를 봅니다.
  - Q. 살아남은 뮤턴트를 어떻게 판단했나요?
    A. 구멍, 동치(동작이 안 바뀌는 변경), 대상 아님(Kotlin이 생성한 코드)으로 나눴습니다. 예를 들어 예약 연장 검증의 `newEnd == 자정` 조건은 앞 검사(같은 날짜, 더 늦은 시각)가 이미 막아 도달할 수 없어서 동치로 보고 운영 코드에서 지웠습니다. 분류는 코드를 읽어 판단하고, 구멍은 변조를 직접 재적용해 확정했습니다.
  - Q. 전체 코드에 적용하지 않은 이유는 무엇인가요?
    A. Controller·Repository·DTO는 로직이 적고 통합 테스트가 느려 시간 대비 얻는 게 적습니다. 핵심 도메인 로직(정책, 가격, 상태 전이, 크레딧)으로 한정해 22~43초로 돌릴 수 있게 했습니다.
  - Q. PIT가 못 하는 것은 무엇이고 어떻게 보완했나요?
    A. 필드 대입과 쿼리(JPQL) 문자열은 변조하지 못합니다. 예약 상태 전이 규칙이 조건부 UPDATE 쿼리에 있어서, 수동으로 20가지씩 변조해 확인했습니다. 기존 서비스 테스트가 Repository를 mock으로 대체해 쿼리를 실행하지 않았다는 사실도 이때 알았습니다. 단점은 재현성이 낮다는 것이라 변조 목록과 결과를 보고서로 남겼습니다.
  - Q. AI가 쓴 코드를 AI가 검증하면 같은 오류를 반복하지 않나요?
    A. 그래서 구현(Codex)과 검증(Claude)을 다른 세션으로 분리했고, 검증자는 보고서 수치를 믿지 않고 전체 테스트와 변조를 직접 재실행했습니다. 그 과정에서 "돈 관련 구멍"이라는 과장, Gradle 캐시로 5초 만에 끝난 가짜 통과, 컨텍스트 로딩 실패로 우연히 잡힌 약한 kill 4건을 걸러냈습니다. 최종 책임은 사람의 확인에 둡니다.
  - Q. 이 작업의 한계는 무엇인가요?
    A. 구멍 개수는 심각도를 반영하지 않습니다. `ChargeOrder`의 구멍 5개는 보조 메타데이터라 작은 구멍이고, 장부-예약 연결이나 마감 검사가 더 의미가 큽니다. 또 수동 변조의 `SET status` 계열 4건은 단언이 아니라 쿼리 오류로 잡혀 증거가 약합니다. CI에는 넣지 않고 수동으로 실행합니다.
  - Q. 구멍이 없는 곳도 있었나요?
    A. `DoorAccessTimePolicy`는 16개, `PricingService`는 4개 전부 잡혔고, 돈이 오가는 핵심(주문 상태, 잔액, 원장)도 이미 탄탄했습니다. 구멍을 못 찾은 곳도 확인한 결과입니다.
  - Q. 점수 목표는 있었나요?
    A. 없었습니다. 점수를 쫓으면 동치 뮤턴트까지 억지로 죽이는 형식적 테스트가 늘기 때문에, 구멍 개수와 대표 사례로 기록했습니다.
- **숫자·근거 한 줄:** 구멍 16개, 추가한 테스트 21개(직접 죽인 16개 + 경계 고정용 5개), 정책 2개·`PricingService`는 뮤턴트 43개 중 43개 잡힘, 전체 테스트 175개 클래스·1,322건 통과(`cleanTest`, 실패 0). PIT 실행은 단위 테스트 한정 시 약 22~43초.
