# AI가 쓴 테스트의 약점을 뮤테이션 테스트(PIT)로 확인한다

> **상태:** 채택 (2026-10-26, 사용자 확인). 0~4단계와 후속 #154까지 구현·검증했고 5~6단계가 남았다. 범위·순서는 [plans/mutation-testing](../plans/mutation-testing/00-mutation-testing-plan.md)에 있고 여기에 복사하지 않는다.

## 한 줄 요약

AI가 작성하거나 Kotlin 전환 중 옮긴 테스트가 "틀렸는데 통과"하거나 "빠져 있는" 경우를 찾기 위해, 프로덕션 코드를 일부러 바꿔 보고(뮤턴트) 테스트가 실패하는지 보는 뮤테이션 테스트 도구 PIT(Pitest)를 핵심 도메인 로직에 한정해 도입한다.

## 1. 문제와 배경

- 2차 프로젝트 보완·기능 추가 과정에서 테스트가 많이 늘었고, 3차에서 Java → Kotlin 마이그레이션을 거쳤다. 이 과정에서 AI가 테스트를 작성·변환했다. 외부 피드백으로 "AI 테스트가 틀렸는데 통과하거나 누락된 테스트가 있을 수 있으니 확인이 필요하다"는 지적을 받았다.
- 테스트 수와 라인 커버리지는 이 문제를 잡지 못한다. 단언(assert)이 약하거나 경계값이 빠져도 줄은 실행되고 테스트 수는 그대로다. [`kotlin-test-guardrails.md`](kotlin-test-guardrails.md)의 테스트 수 하한도 같은 한계를 인정한다(§6: "테스트 수가 같아도 단언이 약해진 경우는 잡지 못한다").
- 이미 수동 뮤테이션을 한 적이 있다. 전환 중 `ReservationTimePolicy` 검증에서 나노초 검사를 일부러 빼 보고 새 테스트 2개가 실패하는 것을 확인했다([`step-1.md`](../lab/notes/kotlin-thursday-policies/step-1.md) 45행). 이를 자동화·일반화하는 것이 이번 결정이다.
- 제약: 일정(3차 마지막 주), 테스트 중 통합 테스트는 Testcontainers(MySQL)를 써서 느리다. Java 테스트(약 128개 파일)와 Kotlin 테스트(약 38개 파일)가 섞여 있다. `AGENTS.md` 규칙상 구현은 한 단계씩, 결정 문서가 먼저다.

## 2. 선택과 이유

- 선택한 방법: Gradle 플러그인 PIT(Pitest)를 추가하고, **단위 테스트로 빠르게 돌릴 수 있는 핵심 도메인 로직**에만 적용한다. 살아남은 뮤턴트를 읽고 테스트를 보강한다.
- 이유:
  - 도구가 기계적으로 코드를 바꾸므로 "AI가 쓴 코드와 테스트를 AI가 다시 검토"하는 순환을 피한다. 사람이 살아남은 뮤턴트를 판단한다.
  - 1차 대상 정책 클래스(`ReservationTimePolicy`, `ReservationRefundPolicy`)는 이미 스프링 없는 단위 테스트가 있어 실행이 빠르다.
  - 의존성은 Gradle 플러그인 한 개 수준이고 운영 코드에 영향이 없다.
- 적용 대상 우선순위와 제외 대상은 plan §2에 둔다.
- 사용자 결정 (2026-10-26):
  - 목표: 포트폴리오 서사가 우선이다. 품질 게이트(점수 미달 시 CI 차단)는 목표가 아니다.
  - 범위: 본인(이태호) 담당 도메인에서 정책 클래스로 시작해 `PricingService`, 상태 전이(`Reservation`, `ChargeOrder`)까지 넓히고, 이후 다른 팀원 담당 클래스(`DoorAccessTimePolicy`, `SpaceOperatingHoursPolicy`, `CreditService`)까지 포함한다.
  - 진행 방식: 한 사람이 PIT 설정·실행·측정·테스트 추가를 모두 맡아 설정과 기준을 하나로 유지한다. 다른 팀원 담당 클래스의 테스트는 새 파일로 추가하고, PR은 해당 담당자의 리뷰를 받는다.
  - 실행: CI에 넣지 않고 수동으로 실행한다. 실행 시간을 측정한 뒤 편입 여부를 다시 본다.
  - 성과 기록: 점수 목표는 두지 않는다. 전/후 점수는 참고로 적고, 발견한 구멍 N개, 추가한 테스트 M개, 대표 사례 3개로 기록한다. 대표 사례는 새로 추가한 테스트뿐 아니라 기존 테스트가 뮤턴트를 잘 잡은 경우에서도 고를 수 있다.

## 3. 기각한 대안과 이유

| 대안 | 장점 | 기각한 이유 |
| --- | --- | --- |
| 라인·분기 커버리지(JaCoCo)만 사용 | 설정이 쉽고 실행이 빠르다 | 코드가 실행됐는지만 보고 단언이 맞는지는 모른다. 지적받은 "틀렸는데 통과"를 못 잡는다. |
| 사람이 테스트를 전수 코드 리뷰 | 도구가 필요 없다 | 테스트 수천 건을 읽는 비용이 크고 놓치기 쉽다. 이미 AI 작성분을 사람이 보는 것이 병목이다. |
| 수동 뮤테이션(코드를 직접 바꿔 보기)만 계속 | 이미 해 본 방식이고 도구 비용이 없다 | 반복·재현이 어렵고 범위가 사람 주의에 달려 있다. 첫 시도로는 유효했으나 확장성이 없다. |
| LLM에게 테스트를 다시 검토시키기 | 설정 없이 바로 가능 | 같은 계열의 오류를 반복할 수 있고 검증 결과가 재현되지 않는다. 보조 수단으로만 쓴다. |
| 전체 코드베이스에 적용 | 한눈에 점수가 나온다 | Controller·Repository·DTO·설정은 로직이 적고 통합 테스트 실행이 느려 시간 대비 얻는 것이 적다. 노이즈 뮤턴트도 늘어난다. |

## 4. Trade-off

| 얻는 것 | 잃는 것(비용·위험) | 완화책 |
| --- | --- | --- |
| 테스트가 실제로 버그를 잡는지 객관적 근거 | 실행 시간 증가(뮤턴트마다 테스트 재실행) | 대상 클래스·테스트를 한정, CI 상시 실행은 보류 |
| 누락된 경계값·약한 단언 발견 | Kotlin 컴파일러 생성 코드(null 체크, `when`)에서 의미 없는 뮤턴트 | 점수보다 살아남은 뮤턴트를 개별로 읽고 동치 뮤턴트는 사유를 적어 제외 |
| "AI 코드를 사람이 검증했다"는 재현 가능한 증거 | 점수 숫자만 쫓으면 형식적 테스트가 늘 수 있음 | 목표 점수 대신 "발견한 구멍과 보강한 테스트" 기록을 성과로 삼는다 |

## 5. 검증 (검증 계획, 구현 후 "검증 결과"로 바꾼다)

- 대상 클래스별로 도입 전 점수와 살아남은 뮤턴트 목록을 기록한다.
- 살아남은 뮤턴트를 "테스트 구멍 / 동치 뮤턴트 / 대상 아님"으로 분류하고, 구멍은 테스트를 추가해 죽인다(테스트 먼저 작성·실패 확인 원칙 적용).
- 도입 후 점수(참고)와 발견한 구멍 N개, 추가한 테스트 M개, 대표 사례 3개(뮤턴트, 테스트, 결과)를 이 절에 적는다. 대표 사례는 기존 테스트에서 골라도 된다.
- 실행 시간을 기록해 CI 편입 가능 여부를 판단한다.
- 점수 100% 달성은 목표가 아니다.

**구멍 5건과 그 의미 (과장 주의)**

| 변조 | 구멍인 이유 | 운영에서의 영향 |
| --- | --- | --- |
| `markPaid`: `failureCode = null` 제거 | 기존 승인 테스트가 성공 후 주문 필드를 확인하지 않음 | 운영에서 `markPaid`는 `CONFIRMING`에서만 호출되고 `failureCode`는 `markFailed`(FAILED)에서만 채워지므로, 이 시점의 값은 이미 null이다. **운영 경로에서는 관찰되지 않는 동작**이며, 신규 테스트는 `FAILED` 주문에 `markPaid`를 호출하는 비현실적 순서로 이를 고정한다 |
| `markPaid`: `recoveryNextAttemptAt = null` 제거 | 같은 이유 | `CONFIRMING`에서는 값이 있을 수 있다. 다만 복구 후보 조회가 `status`로 거르므로 PAID 주문이 후보가 되지 않아 동작은 같고, 남는 것은 잘못된 메타데이터다 |
| `markPaid`: `updatedAt = now → createdAt` | 갱신 시각을 단언하지 않음 | 승인 시각 기록 오류 |
| `markFailed`: `recoveryNextAttemptAt = null` 제거 | 위와 같음 | 위와 같음 |
| `markFailed`: `updatedAt = now → createdAt` | 위와 같음 | 위와 같음 |

- **돈이 오가는 핵심(상태 `PAID` 전이, 잔액 증가, 원장)은 이미 기존 테스트가 잡았다**(`markPaid`의 `PAID→FAILED`, `markFailed`의 `FAILED→PAID` 변조는 각각 15건·9건 실패). 구멍 5건은 주문의 **보조 메타데이터(실패코드·복구 예약·갱신 시각) 정리**이며 금액이 틀어지는 종류가 아니다. 구현자 보고서의 "돈 관련 대표 사례"라는 표현은 과하므로 포폴·발표에서는 "돈 경로는 기존 테스트가 탄탄했고, 보조 상태 정리가 비어 있었다"로 쓴다.
- 구멍 1번(`failureCode`)은 운영에서 동치에 가깝다. 신규 테스트가 비현실적 순서를 쓴다는 점을 구현자도 보고서에 적었다.
- 열린 질문(팀 판단): `markPaid`·`markFailed`가 엔티티 내부에서 출발 상태(`CONFIRMING`)를 검사하게 할지. 지금은 서비스가 호출 전에 검사하므로 운영은 안전하지만, public 메서드 자체는 `FAILED → PAID` 재개방을 막지 않는다. #155(엔티티 전이 메서드 삭제 여부)와 함께 논의하는 것이 자연스럽다.

**검증 중 발견한 한계·주의**
- PIT는 필드 대입을 변조하지 못한다. 오픈소스 PIT에는 대입용 mutator가 없다(`MEMBER_VARIABLE`은 unknown으로 거부됨). 그래서 `ChargeOrder.markPaid`·`markFailed`·`markRecoveryExhausted` 등 돈이 오가는 상태 전이 메서드에는 뮤턴트가 0건이다. 이 메서드들의 전이는 PIT로 검증되지 않았다. 필요하면 쿼리처럼 수동 변조로 별도 확인한다(후속 후보).
  - 후속 이슈 #154에서 `ChargeOrder` 전이 메서드를 수동 변조로 검증했다(아래 "#154 검증 결과").
- 수동 변조 중 `SET status` 계열 4건(`cancelIfHeld`, `forceCancelIfStatusIs`, `checkInIfConfirmed`, `checkOutIfInUse`)은 변조하면 쿼리의 파라미터가 하나 남아 Spring이 컨텍스트를 못 띄우므로 테스트가 대량으로 실패한다. 단언이 잡은 증거가 아니다. 예: `cancelIfHeld`의 `SET status = :cancelled → :held`는 쿼리에서 `:cancelled` 파라미터가 사용되지 않아 Spring이 쿼리를 거부하므로, 새 통합 테스트 8건이 모두 컨텍스트 로딩 실패로 실패한다. "상태가 CANCELLED로 바뀌었는가" 단언이 아니라 쿼리 검증에 의해 죽은 것이다. 같은 의미의 오류(다른 상태로 설정)는 단언 테스트(`HELD cancellation changes status and records the cancellation time`)가 잡아야 하지만 이 변조 방식으로는 분리해 확인하지 못했다.
- Codex가 변조하지 않은 후보 조회 쿼리 3개(`findExpiredHoldIds`, `findNoShowCandidateIds`, `findAutoCheckOutCandidateIds`)가 같은 경계 조건을 가진다. UPDATE가 조건을 다시 검사하므로 위험은 낮지만 미검증이다.
- 노쇼 정각 경계 테스트는 Repository 파라미터(`startTimeBefore`)에 직접 값을 넣는다. 파라미터를 `now - 15분`으로 계산하는 `ReservationBatchProcessor`의 계산 자체는 경계에서 검증하지 않는다.
- `Reservation` 엔티티의 전이 메서드 7개는 운영 코드에서 호출되지 않는다. 전이 규칙이 엔티티와 쿼리에 중복돼 어긋날 위험이 있다. 삭제 여부는 팀 판단으로 남아 있다(보고서의 질문 1).
- 노쇼 정각 경계(보고서의 질문 2): 현재 쿼리의 `startTime < now - 15분`(정각까지는 NO_SHOW 아님)은 `access-key-policy.md`의 최초 체크인 구간 `[start, start+15분]`(닫힌 구간)과 일치한다. 정각 `start+15분`에 체크인할 수 있어야 하므로 노쇼는 그 이후여야 한다. 코드 변경 없이 유지하면 된다.
- CI에서의 전체 테스트 통과는 PR을 올린 뒤 확인한다(이 검증은 로컬 Docker 환경).

## 6. 한계와 재검토 조건

- 뮤테이션 테스트는 단위 수준의 단언 품질을 본다. 동시성·멱등성 같은 경합 문제는 뮤턴트로 잡히지 않으므로 기존 통합 테스트가 계속 필요하다.
- 동치 뮤턴트(동작이 안 바뀌는 변경)는 사람이 판단해야 한다.
- 재검토 조건: 실행 시간이 허용 범위를 넘거나, Kotlin 노이즈로 신호가 묻히거나, 대상 확장 후에도 새 구멍이 나오지 않으면 범위를 줄이거나 도구를 바꾼다.
