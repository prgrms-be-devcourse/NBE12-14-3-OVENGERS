# 테스트는 코드와 함께 Kotlin으로 옮기되 테스트 수 하한과 골든 파일로 약해지지 않게 지킨다

> **상태:** 채택 (2026-10-22, 사용자 확인: grill 세션). 아직 구현 전이다. 새 기준선 숫자는 CI 실행 후 [테스트 결과](../testing/test-results.md)에 기록한다.

## 한 줄 요약

운영 코드를 옮길 때 그 테스트도 같이 Kotlin으로 옮기되, (1) CI가 테스트 실행 수가 기준선 이상이고 스킵이 0인지 자동 검사하고, (2) 옮기기 전 Java의 API 응답을 골든 파일로 저장해 전환 후 같은 JSON인지 테스트로 비교한다.

## 1. 문제와 배경

- 기준선은 2026-10-20 `d1a15ec`의 1,048건 통과(스킵 0, `@Disabled` 0)이다. 이후 `build.gradle`에 Kotlin 플러그인이 들어왔으므로 현재 `dev`에서 CI로 다시 측정해야 한다. 이 PC에서 측정을 시작했지만 기준선으로 쓰는 값은 CI 실행 결과다.
- 테스트도 같이 옮기면(사용자 결정) 어려운 테스트가 막혀 `@Disabled`를 붙이거나 지우는 일이 생겨도 `./gradlew build`는 초록불이다. 검사 항목이 줄어든 것을 빌드는 알려주지 않는다.
- "전환 전후 HTTP가 같다"를 눈으로 비교하는 것은 신뢰할 수 없다. 필드 누락·`null`·날짜·숫자 형식은 사람이 놓치기 쉽다.
- 현재 [`backend-ci.yml`](../../.github/workflows/backend-ci.yml)은 `./gradlew build`만 실행하고 테스트 수는 검사하지 않는다.

## 2. 선택과 이유

- **테스트도 운영 코드와 같은 PR에서 Kotlin으로 옮긴다.** 단, `assertThat(...)` 같은 판정 줄(기대값)은 바꾸지 않고 문법만 바꾼다.
- **CI에 테스트 수 검사 단계를 추가한다.** `backend/build/test-results/test/*.xml`의 `tests` 합계가 기준선 이상이고 `skipped`가 0이 아니면 실패한다. 스킵이 정말 필요한 경우 PR에 사유를 적고 기준선 문서를 갱신한다. 새 테스트가 추가되면 기준선도 그만큼 올린다.
- **골든 파일 테스트를 전환 전에 Java 코드에서 먼저 만든다.** 대상은 로그인, 충전, 예약, 결제, 출입, 문의, 오류 응답이고, 필드 누락·`null`·날짜·숫자 형식을 포함한다. 동적 ID·시각은 입력을 고정하거나 형식으로 검증해 취약한 전체 문자열 비교를 피한다([03 API 계약](../plans/kotlin-migration/03-api-contract.md)).
- 이유: 테스트를 같이 옮기는 방식에서 "테스트가 약해지지 않았다"를 사람의 주의가 아니라 숫자와 파일로 확인하게 한다.

## 3. 기각한 대안과 이유

| 대안 | 장점 | 기각한 이유 |
| --- | --- | --- |
| 기존 Java 테스트는 마지막까지 두고 새 테스트만 Kotlin | 기존 테스트가 변하지 않는 "자" 역할을 한다 | 사용자가 테스트도 같이 옮기기를 선택했다(2026-10-22). 위험은 아래 보호 장치로 줄인다. |
| 사람이 PR 설명에 테스트 수를 적고 리뷰어가 확인 | CI 변경이 없다 | 숫자를 옮겨 적다 놓칠 수 있다. 자동 검사가 정확하다. |
| 테스트 수 검사 없이 `./gradlew build` 통과만 확인 | 가장 단순하다 | 테스트가 조용히 줄어도 통과한다. |

## 4. Trade-off

| 얻는 것 | 잃는 것(비용·위험) | 완화책 |
| --- | --- | --- |
| 테스트와 운영 코드를 함께 옮기는 PR의 일관성 | 테스트가 틀렸을 때 코드 문제인지 테스트 문제인지 구분이 어렵다 | 판정 줄은 바꾸지 않는 원칙, 테스트 수 하한, 골든 파일(전환 전 Java에서 만든 기준) |
| 테스트 수 하한이 자동으로 지켜짐 | CI 스크립트 한 단계와 기준선 갱신 비용 | 기준선 측정 PR과 합쳐서 한 번에 넣는다. |
| 골든 파일로 JSON 호환을 객관적으로 확인 | 동적 필드가 있는 응답은 비교가 까다롭다 | 동적 값은 고정하거나 형식으로만 검증한다. |

## 5. 검증

**검증 계획:** (1) CI 단계가 테스트를 일부러 하나 줄였을 때 실패하는지, 스킵을 넣었을 때 실패하는지 확인한다. (2) 골든 파일 테스트는 Java 코드에서 통과한 뒤, Kotlin 전환 후에도 같은 파일로 통과해야 한다. 결과는 구현 후 이 절에 적는다.

## 6. 한계와 재검토 조건

- 테스트 수가 같아도 단언이 약해진 경우는 이 검사가 잡지 못한다. 리뷰에서 판정 줄 변경 여부를 확인한다. 이 한계는 [뮤테이션 테스트](mutation-testing.md)로 보완했다(핵심 도메인 로직 한정, 수동 실행, 2026-10-26).
- 서비스 파라미터가 Kotlin non-null이 되면 Mockito 매처(`any()`, `eq()`, `capture()`는 `null`을 반환)가 호출 시점에 NPE를 낸다(2026-10-24 step-05 전체 빌드에서 8건). 서비스 파라미터를 nullable로 느슨하게 하지 않고 테스트 쪽에서 값을 그대로 돌려주는 헬퍼(`eqNonNull`, `captureNonNull` 등)로 고친다. 직접 대응 테스트만 돌리면 놓치므로 변환한 클래스를 참조하는 테스트 전체를 실행한다. 같은 문제가 여러 파일에서 반복되면 mockito-kotlin 도입을 재검토한다.
- 전환이 끝난 뒤 골든 파일을 계속 유지할지, 일반 계약 테스트로 흡수할지 재검토한다.
