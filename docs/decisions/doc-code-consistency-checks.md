# 문서가 코드와 어긋나는 것을 사람 기억이 아니라 자동 검사와 단계별 대조로 잡는다

> **상태:** 채택, 구현 반영(2026-10-27, PR #179~#182). 이 결정은 `AGENTS.md`의 "새 기술은 구현 전에 결정 문서를 쓴다"는 순서와 다르게 **구현을 먼저 하고 사후에 기록**했다. 대조 작업 자체가 어디를 검사할지 알아 가는 과정이었기 때문이며, 이 점을 한계에 적었다. 단계별 보고는 [`testing/doc-verification/`](../testing/doc-verification/)에 있고 여기에 복사하지 않는다.

## 한 줄 요약

문서가 틀릴 수 있다는 전제에서, 기계가 확인할 수 있는 주장(엔드포인트·에러 코드·테이블·컬럼·FK)은 스크립트로 CI에서 매 PR마다 대조하고, 의미 판단이 필요한 주장(규칙과 테스트의 대응, 오류 목록, DTO 필드)은 범위를 좁혀 근거(파일·줄)와 함께 단계별로 대조한다.

## 1. 문제와 배경

- 프론트가 `api-spec.md`를 기준으로 연동하고(`api-spec.md` 9줄), AI 에이전트가 `AGENTS.md`·`erd.md`를 읽고 구현한다. 이 문서들이 코드보다 늦게 갱신되면 잘못된 구현 근거가 된다.
- 실제로 어긋난 사례를 단계별 대조에서 확인했다(§5). 가장 큰 것은 `AGENTS.md` 규칙 3이 "매 요청 DB를 재조회하지 않는다"고 했지만 PR #350 이후 인증 필터는 DB 세션과 회원 `ACTIVE` 상태를 매 요청 확인한다는 점이다. 테스트는 새 동작을 지키고 있었고 문장만 낡아 있었다.
- 강사 피드백: 문서는 틀릴 수 있다. 그러나 "틀릴 때마다 사람이 갱신한다"는 방식은 갱신이 빠지는 지점(작은 NULL 컬럼 추가 등)에서 반복해서 샌다.
- 제약: 일정(10/22~10/28 Kotlin 전환 중), 팀 규칙(문서 커밋과 코드 커밋 분리, 기능 동결 후 코드 변경 최소화), 공유 체크아웃에서 여러 세션이 동시에 작업.

## 2. 선택과 이유

- 선택한 방법:
  1. **정답의 우선순위를 정한다:** 테스트가 통과하는 코드 > `core-domain-decisions` > `decisions/*` > `api-spec`·`erd` > README·plans. 충돌하면 위쪽이 이긴다. `decisions/*`는 시점 기록이라 검증 대상이 아니다.
  2. **기계 확인이 가능한 주장은 스크립트 + CI:** `.github/scripts/check_api_spec.py`(컨트롤러 경로·`ErrorCode` enum ↔ `api-spec.md`), `check_erd.py`(Flyway V1~V26이 만드는 최종 스키마 ↔ `erd.md`). 각각 단위 테스트가 있어(8개, 9개) 스크립트가 실제로 불일치를 잡는지(탐지력)를 확인한다.
  3. **의미 판단이 필요한 주장은 사람/LLM이 단계별로, 근거를 달아 대조:** 규칙 1–7 ↔ 테스트 매핑, 핵심 도메인 엔드포인트 19개의 오류 목록, DTO 19개의 필드. 판정마다 파일과 줄 근거를 달고 "일치 / 불일치 / 확인 불가"로 나눈다.
  4. **모델은 대조 성격에 맞춘다:** 표를 읽고 grep으로 비교하는 일은 Sonnet급으로 충분했고, 판단이 애매한 항목만 상위 모델로 재확인하는 2단 구성을 쓴다(이번에는 재확인할 항목이 나오지 않았다).
- 이유:
  - 같은 대조를 LLM에게 매번 시키면 읽지 못한 범위가 "문제 없음"으로 답해질 수 있고 결과가 재현되지 않는다. 스크립트는 같은 입력에 같은 결과를 낸다.
  - 문서를 코드에서 생성하는 대신 대조하는 이유: 문서에는 의도·이유·정책이 섞여 있어 생성물로 대체할 수 없다.
  - 근거: 단계별 보고서 [step-1](../testing/doc-verification/step-1.md) ~ [step-4](../testing/doc-verification/step-4.md).

## 3. 기각한 대안과 이유

| 대안 | 장점 | 기각한 이유 |
| --- | --- | --- |
| "모순 찾아줘"를 LLM에 통째로 맡긴다 | 가장 빠르다. 추가 구현이 없다. | 읽지 못한 범위를 "없음"이라고 답할 수 있고, 재현이 안 되며, 변경 후에도 유효하다는 보장이 없다. |
| 변경할 때마다 사람이 문서를 갱신한다 | 도구가 필요 없다. | 작은 변경(NULL 컬럼 추가, 에러 코드 추가)에서 갱신이 빠지는 것을 실제로 확인했다(`erd.md` 컬럼 3개, `api-spec.md`의 `PATCH /members/me`와 `MEMBER_WITHDRAWN`). |
| 서비스 호출 경로의 에러 코드를 정규식으로 추출해 문서 오류 목록과 자동 비교 | 오류 목록까지 CI에서 지킬 수 있다. | 서비스가 다른 빈·엔티티·정책 클래스를 거치는 호출 경로를 정규식으로 따라가기 어렵고, 방어적으로만 던지는 코드(필터가 먼저 막아 사실상 도달하지 않는 `ACCOUNT_WITHDRAWN` 등)가 위양성이 된다. 사용자가 하지 않기로 결정(2026-10-27). 대신 "문서의 오류 코드마다 그 코드를 확인하는 테스트가 있는가"를 매핑하는 방식을 필요할 때 검토한다. |
| Testcontainers로 실제 MySQL에 마이그레이션을 적용한 `information_schema`와 `erd.md` 대조 | SQL을 정규식으로 해석하는 오류가 없다. | 이번 범위에서는 비용(CI 시간, Docker)이 이득보다 크다고 판단해 보류. 현재 26개 마이그레이션은 파서로 모두 해석된다. |
| 아키텍처 테스트(ArchUnit)로 `AGENTS.md` 규칙 7의 의존 방향을 강제 | 규칙을 코드로 강제한다. | 새 의존성이 필요하고, 지금도 `credit`이 `Reservation` 엔티티·저장소를 import해 패키지 단방향 규칙을 쓰면 도입 즉시 실패한다. 규칙이 지키려는 것은 호출 방향이어서 규칙 문장을 정리하는 쪽으로 해결(§6). |
| `AGENTS.md`를 CI에서 검사 | 규칙 파일의 에러 코드도 지킬 수 있다. | `AGENTS.md`가 `.gitignore` 대상이라 CI 체크아웃에 없다. 스크립트는 파일이 있을 때만 검사한다. |

## 4. Trade-off

| 얻는 것 | 잃는 것(비용·위험) | 완화책 |
| --- | --- | --- |
| 컨트롤러·`ErrorCode`·스키마를 바꾸는 PR이 문서를 같이 고치지 않으면 CI가 실패한다 | 문서 갱신을 잊은 PR이 막혀 개발 속도가 약간 떨어진다 | 실패 메시지가 어느 항목이 빠졌는지 알려준다. 내부 전용 코드는 `INTERNAL_ONLY`에 이유와 함께 등록해 우회한다. |
| 같은 입력에 같은 결과(재현성) | 정규식 해석이라 새 SQL 구문이나 새 어노테이션 형태가 나오면 놓치거나 오탐한다 | 단위 테스트로 오탐 사례(여러 줄 `@PutMapping(value = [...])`, `RENAME TABLE`)를 고정했다. 새 구문이 나오면 스크립트를 먼저 확장한다. |
| 의미 판단이 필요한 부분을 근거와 함께 기록 | 단계별 수동 대조라 다시 어긋날 수 있고, 사람이 매번 해야 한다 | 대조 범위를 핵심 도메인으로 좁혔고, 자동화하지 않은 부분은 한계에 적었다. |
| 문서 오류를 숫자로 설명할 수 있다 | 최초 대조와 스크립트 작성 비용이 든다 | 기계 검사는 한 번 만들면 이후 PR마다 자동으로 돈다. |

### 검증 계획: 규칙 4 테스트 인계 (구현 세션용, Codex)

`AGENTS.md`의 역할 규칙에 따라 구현은 구현 세션이, 검증은 새 세션이 맡는다. 인계는 이 절로 한다.

- 목적: 규칙 4(관리자 권한 ≠ 소유권)를 테스트로 고정한다. 현재 "타인" 테스트의 호출자는 모두 일반 회원이라 **ADMIN 역할 JWT**로 사용자 전용 엔드포인트를 호출하는 경우가 비어 있다.
- 위치: `backend/src/test/kotlin/com/ovengers/slotkey/reservation/controller/` 아래 새 통합 테스트 클래스(Kotlin). 준비 코드는 `DoorAccessSecurityIntegrationTest`(`access/service`)를 따른다: `ReservationIntegrationTestSupport` 상속, `@AutoConfigureMockMvc`, `@Import(SettableClockConfig::class)`, `issueSessionBoundAccessToken(member, jwtProvider)`. 이 지원 클래스는 Testcontainers MySQL을 쓰므로 **Docker가 필요하다.**
- 준비: 소유자 회원, 공간, 예약. 관리자는 `createMember(0)`으로 만든 뒤 `UPDATE member SET role = 'ADMIN'`으로 바꾸고 그 회원의 세션 JWT를 쓴다(`ReservationHttpSupplementGoldenTest`의 force-cancel 준비와 같은 방식).
- 기대 동작: 아래 호출이 모두 **403 `FORBIDDEN_NOT_OWNER`**.

  | 호출 | 사전 상태 |
  | --- | --- |
  | `POST /api/v1/reservations/{id}/cancel` | `CONFIRMED`, 시작 전 |
  | `POST /api/v1/reservations/{id}/extend` | `CONFIRMED` |
  | `POST /api/v1/reservations/{id}/pay` (헤더 `Idempotency-Key`, 바디 `spaceVersion`) | `HELD` |
  | `POST /api/v1/reservations/{id}/check-out` | `IN_USE` |
  | `POST /api/v1/reservations/{id}/door-token` | `CONFIRMED` |
  | `PATCH /api/v1/reservations/{id}/access-token/revoke` | 활성 토큰 있음 |
  | `GET /api/v1/reservations/{id}/access-logs` | `CONFIRMED` |

- 호출 뒤 확인(부작용 없음): 예약 상태·슬롯 수 불변, 소유자 잔액과 원장 불변, 활성 도어 토큰 불변, `idempotency_key` 행 0건(pay), `audit_logs` 행 0건.
- 대조군(테스트가 공허하지 않음을 보이기): 같은 상황에서 소유자 JWT로 한 엔드포인트(예: cancel)는 403이 아니고 성공해야 한다. 관리자 JWT로 `POST /api/v1/admin/reservations/{id}/force-cancel`은 성공해야 한다.
- 이 테스트는 현재 동작을 고정하는 보호용이라 처음부터 통과한다. "실패 먼저" 순서가 적용되지 않으므로 **소유권 검사를 잠깐 깨뜨려(예: 서비스에서 역할이 ADMIN이면 통과시키도록 수정) 테스트가 실패하는지 확인한 뒤 되돌린다.** 확인 결과를 보고서에 적는다.
- 보고: `docs/testing/rule4-admin-ownership/step-1.md`에 `AGENTS.md`의 인계 보고 항목(변경 파일, 실행 명령과 결과, 가정, 관련 결정 문서)을 남긴다. 검증은 새 세션이 한다.

### 규칙 4 구현 세션의 검증 결과 (2026-10-27, 독립 검증 대기)

- `AdminRoleOwnershipIntegrationTest`에 ADMIN 세션 JWT의 7개 거부 사례와 소유자 취소·관리자 전용 강제 취소 성공 대조군 2개를 추가했다. 거부 전후 예약·슬롯·잔액·원장·토큰·멱등키·감사 로그를 비교한다.
- 기존 운영 코드에서 신규 9개가 통과했다. 소유권 거부 조건 5곳을 일시 우회하면 거부 사례 7개가 모두 실패하고 대조군 2개는 통과했다. 운영 소스는 원복했으며 실험의 후속 오류와 한계도 보고에 구분했다.
- 원복 후 `ktlintCheck`와 전체 `test`가 통과했다(1,370개, 실패·오류·스킵 0). 운영 소스 diff는 비어 있다.
- 최종 전체 실행 수치, 원복 확인, 변경 파일과 새 세션의 리뷰 체크리스트는 [규칙 4 step-1 구현 인계](../testing/rule4-admin-ownership/step-1.md)에 기록한다. 이 결과는 구현 세션의 직접 실행이며 별도 검증 세션·CI·사람 리뷰를 대체하지 않는다.

## 6. 한계와 재검토 조건

- **사후 기록:** `AGENTS.md`는 새 기술 도입 전에 결정 문서를 쓰라고 하지만 이번에는 구현이 먼저였다. 앞으로 대조 범위를 늘릴 때는 이 문서를 먼저 갱신한다.
- **알고 남긴 테스트 공백(보강하지 않음):**
  - 규칙 5: 같은 예약에 활성 도어 토큰 행을 직접 두 번 INSERT하면 DB가 거절하는지 보는 테스트가 없다. 동시성 테스트(`DoorAccessTokenConcurrencyTest`)가 "활성 토큰 정확히 1개"를 실제 DB로 확인하므로 간접 검증은 있다. 낮은 우선순위로 판단해 보강하지 않았다.
  - 규칙 7: 의존 방향을 강제하는 테스트가 없다. 아키텍처 테스트를 도입하지 않고 규칙 문장을 호출(제어) 방향 기준으로 좁혔다. 현재 코드는 호출 방향을 지키며(`reservation`은 `CreditService` 포트만 호출) 원장이 예약을 참조하는 데이터 의존은 규칙 대상이 아니다.
- **자동 검사의 범위:** 엔드포인트·에러 코드의 존재와 상태 코드, 테이블·컬럼·UNIQUE·FK만 자동이다. 컬럼 타입, CHECK, 인덱스 설명, 오류 목록(엔드포인트별), DTO 필드, 성공 HTTP 상태, 요청 검증 제약은 자동 검사하지 않는다. 오류 목록·DTO는 핵심 도메인 3개만 수동으로 대조했고 나머지 도메인(member, space, auth, inquiry, waitlist, stats, audit)은 대조하지 않았다.
- **미결:** 관리자 예약 상세에 `holdExpiresAt`이 필요한 요구가 있었는지 확인되지 않았다. 문서를 코드에 맞춰 두었고, 필요하다면 문서가 아니라 코드를 고쳐야 한다.
- **`AGENTS.md`는 git이 추적하지 않는다:** 개정한 규칙 3·6·7은 로컬 파일에만 반영되어 있고 PR에는 들어가지 않는다. 팀에 공유하려면 별도로 전달해야 한다.
- **전체 테스트 미실행:** 규칙 1–7 매핑은 테스트를 읽어서 만들었고 실행해서 확인하지 않았다.

## 면접·발표용 정리 (구현 후)

- **30초 설명:** 문서는 틀릴 수 있다는 전제에서, 사람이 기억해서 갱신하는 대신 기계가 확인할 수 있는 것은 스크립트로 CI에 넣고(API 문서와 코드, ERD와 DB 마이그레이션), 판단이 필요한 것은 범위를 좁혀 근거와 함께 대조했습니다. 그 결과 `api-spec`·`erd`의 불일치 12건과 `AGENTS.md`의 낡은 에러 코드 3개·규칙 문장 2개를 찾았고, 가장 큰 것은 인증 규칙이 구현과 반대로 적혀 있던 점입니다.
- **예상 질문과 답:**
  - Q. 왜 LLM에게 문서 검증을 통째로 맡기지 않았나요?
    A. 읽지 못한 범위를 "문제 없음"으로 답할 수 있고, 같은 질문에 결과가 달라지며, 변경 뒤에도 유효한지 알 수 없습니다. 그래서 기계 확인이 가능한 부분은 스크립트와 CI로 바꿨고, LLM은 판단이 필요한 부분을 근거와 함께 대조하는 데만 썼습니다.
  - Q. 이 방식의 단점은 무엇이고 어떻게 보완했나요?
    A. 정규식 해석이라 새 구문에서 틀릴 수 있어서, 오탐 사례를 단위 테스트로 고정하고 검사가 실제로 불일치를 잡는지(탐지력)를 테스트 17개로 확인했습니다. 오류 목록과 DTO 필드는 자동화하지 않았고 수동 대조라 다시 어긋날 수 있다는 한계는 기록해 두었습니다.
  - Q. 규모가 커지면 어떻게 바꾸겠습니까?
    A. 정규식 해석이 흔들리면 Testcontainers로 실제 DB 스키마와 대조하고, 오류 목록 어긋남이 반복되면 "문서의 오류 코드마다 확인하는 테스트가 있는가"를 CI로 올리겠습니다.
- **숫자·근거 한 줄:** 엔드포인트 65·에러 코드 65·테이블 25·FK 23을 자동 대조하고 핵심 도메인 엔드포인트 19개·DTO 19개를 수동 대조해 문서 쪽 오류를 찾았고, 검사 스크립트의 탐지력은 단위 테스트 17개로 확인했습니다.
