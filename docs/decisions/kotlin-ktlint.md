# ktlint를 Kotlin 전환 시작 전에 먼저 도입한다

> **상태:** 채택 (2026-10-22, 사용자 확인: grill 세션). 아직 구현 전이다. 구현 PR은 `step-0`과 별개의 작은 PR이다.

## 한 줄 요약

5명이 같은 기간에 Kotlin 코드를 만들기 때문에, 코드 모양(들여쓰기·줄바꿈·import 순서)을 자동 검사하는 ktlint를 **Kotlin 파일이 0개인 지금** 기본 규칙으로 먼저 넣고, 위반하면 `./gradlew build`가 실패하게 한다.

## 1. 문제와 배경

- 2026-10-22 현재 `backend/build.gradle`에는 Kotlin 플러그인만 있고 ktlint·detekt·spotless가 없다. `src/main/kotlin`은 아직 없다.
- 10/22~10/27에 5명이 운영 Java 293개, 테스트 Java 148개를 병렬로 옮긴다. 각자 스타일로 쓰면 PR마다 "줄바꿈만 바뀐 줄"이 섞여 진짜 변경을 리뷰하기 어렵다. 나중에 일괄 포맷하면 그 diff가 전체 코드에 퍼진다.
- 제약: 6일 일정, 기능 불변(HTTP·메시지·DB 스키마 유지).

## 2. 선택과 이유

- 선택한 방법: ktlint를 기본 규칙으로 도입하고 위반 시 빌드 실패로 한다. `step-0`과 분리된 작은 PR로 Kotlin 소스가 생기기 전에 머지한다. 구체 Gradle 플러그인(ktlint 직접 또는 spotless의 ktlint 설정)은 Kotlin 1.9.25·Gradle 8.10.2와 호환되는 버전을 구현 PR에서 확인해 고른다.
- 이유: Kotlin 코드가 0개일 때 넣으면 기존 코드를 고칠 일이 없어 도입 비용이 가장 낮다. 규칙을 기본값으로 두면 팀이 규칙을 논의하는 시간이 들지 않는다.

## 3. 기각한 대안과 이유

| 대안 | 장점 | 기각한 이유 |
| --- | --- | --- |
| 도입하지 않고 IDE 기본 포맷에 맡김 | 추가 설정 없음 | IDE마다 설정이 달라 5명의 결과가 같다는 보장이 없다. |
| 전환이 끝난 뒤 일괄 포맷 | 일정 중 설정 부담 없음 | 전체 파일에 포맷 diff가 생기고, 전환 PR 리뷰 중에는 스타일 차이가 섞인다. |
| detekt까지 도입 | 복잡도·스멜 검사 | 이번 범위가 아니다. 규칙 튜닝에 시간이 들고 기능 불변 전환의 목표와 거리가 있다. 필요하면 전환 후 별도 결정. |

## 4. Trade-off

| 얻는 것 | 잃는 것(비용·위험) | 완화책 |
| --- | --- | --- |
| 일관된 스타일, 깨끗한 리뷰 diff | 위반 시 빌드가 실패해 PR이 막힌다 | 로컬에서 자동 정렬(format) 명령을 PR 체크리스트에 적는다. |
| 전환 전에 도입해 기존 코드 수정 불필요 | 도구와 Kotlin 1.9.25의 호환 확인 필요 | 구현 PR에서 빈 Kotlin 파일 하나로 검사가 동작하는지 확인한다. |

## 5. 검증

**검증 계획:** 구현 PR에서 (1) 의도적으로 규칙을 위반한 Kotlin 파일이 `./gradlew build`를 실패시키는지, (2) 자동 정렬 후 통과하는지, (3) Java 코드·기존 테스트 수에 영향이 없는지 확인한다. 결과는 구현 후 이 절에 적는다.

## 6. 한계와 재검토 조건

- 이 선택이 안 맞는 경우: 도구가 Kotlin 1.9.25 또는 Gradle 8.10.2와 맞지 않으면 다른 설정 경로(spotless 등)로 바꾼다.
- 전환 완료 후 코드 품질 규칙(detekt 등)을 늘릴지 별도 결정한다.
