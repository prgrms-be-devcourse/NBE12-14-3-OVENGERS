# 관리자 베스트 공간 랭킹을 매일 00시 확정값으로 제공

> **과거 보고서 참조 안내**: 이 문서에서 언급하는 `docs/lab/notes/`의 보고서 원문은 기능 동결 커밋 `d1a15ec`에 포함되어 있지 않다. 보고서 이름과 당시 결과는 기존 문서의 기록으로 보존하며, 이번 갱신에서 원문을 확인하거나 테스트를 재실행했다는 뜻이 아니다. 해당 보고서 이름에는 링크를 제공하지 않는다.

> 1~4번과 6번은 구현 전에 쓰고, 5번의 "검증 결과"와 면접·발표용 정리는 구현 후(2026-10-16, 단계 1–8)에 채웠다. 설계 합의는 2026-10-16 사용자와의 질의응답(grill-me)으로 이루어졌다. 기존 구현·검증 보고 참조는 lab/notes/space-ranking이었으며, **구현과 검증이 같은 세션이라 "자기검증"이다**(CI와 사람의 확인이 최종 안전망).

## 한 줄 요약

일간·주간·월간 베스트 공간(매출·예약 건수·슬롯 수)은 끝난 기간만 매일 00:01에 한 번 계산해 `space_ranking_snapshot` 테이블에 **확정값**으로 저장하고 보여 주며, 매출은 환불을 환불 발생일에 반영하는 현금주의로 센다.

## 1. 문제와 배경

- 관리자 대시보드에 "어느 공간이 많이 팔리고 많이 예약되는가"를 보여 주는 기능이 없다. 백엔드에 통계·랭킹 엔드포인트가 없고(`Admin*Controller`는 예약·공간·회원·문의·감사 로그뿐), 기존 "운영 대시보드"(`AdminDashboard`)는 `/admin/reservations`를 1000건씩 전부 내려받아 브라우저에서 센다. 코드 주석에도 운영 데이터에서 매우 느렸다고 적혀 있다.
- 매출 정의가 단순하지 않다. 사용자 취소는 시작 1시간 전까지 전액 환불이고, 그 후에는 50% 위약금이 원장에 `REFUND`(+전액)와 `PENALTY`(−50%)로 따로 쌓인다. 관리자 강제취소는 위약금 없는 전액 환불이다. `NO_SHOW`·`EXPIRED`는 환불이 없다. `reservation.total_amount`만 합치면 위약금 수익이 빠진다.
- 취소는 `reservation_slot` 행을 삭제하므로 슬롯 테이블로는 과거 이력을 집계할 수 없다. 집계는 `reservation`과 `credit_transaction`(크레딧 원장)으로 해야 한다.
- 제약
  - 상위 "오피스·지점" 엔터티가 없다. 지역은 `spaces.location`(자유 텍스트: 판교·하남·강남)뿐이다.
  - 가능하면 테이블을 늘리지 않는다(사용자 요구). 지역은 더 늘리지 않을 계획이다.
  - 엔티티는 `LocalDateTime`(시간대 정보 없음)을 쓰고, 화면의 "오늘"은 KST(`Asia/Seoul`)다.
  - Redis·Spring Cache 의존성이 없다. 서버는 단일 EC2다.
  - 신규 코드에는 Lombok을 쓰지 않는다(DTO는 record).

## 2. 선택과 이유

- **선택한 방법**
  1. **순위는 "끝난 기간"만 확정값으로 보여 준다.** 일간은 매일 00:01, 주간은 월요일 00:01, 월간은 1일 00:01에 방금 끝난 기간을 계산해 `space_ranking_snapshot`에 저장한다. 진행 중인 기간(오늘·이번 주·이번 달)은 순위 대신 "집계 중입니다. 오늘 순위는 내일 00:00 기준으로 확정됩니다" 안내만 보여 준다.
  2. **매출은 순매출, 현금주의.** 결제(`RESERVATION_CHARGE`)는 결제 시각에, 환불(`REFUND`)·위약금(`PENALTY`)은 발생 시각에 반영한다. 원장 부호가 회원 기준(차감 −, 환급 +)이므로 공간 매출 = `−SUM(amount)` (`type IN (RESERVATION_CHARGE, REFUND, PENALTY)`, `reservation_id`로 `reservation.space_id`에 조인, `created_at`이 기간 안). 위약금은 수익으로 포함한다.
  3. **예약 건수·슬롯 수는 이용 시작 시각 기준.** `reservation.status IN (CONFIRMED, IN_USE, COMPLETED, NO_SHOW)`이고 `start_time`이 기간 안인 예약만 센다. 슬롯 수는 `(end_time − start_time) / 30분`의 합이며 이름은 "예약 슬롯 수"다.
  4. **기간은 달력 기준, KST, 주는 월요일 시작.** 데이터 범위는 `[기간 시작 00:00:00, 기간 끝 다음날 00:00:00)` 반열린 구간이다. 계산은 끝난 직후 00:01에 시작하고 계산 완료 시각(`computed_at`)을 함께 저장·표시한다.
  5. **단위는 공간과 지역 둘 다.** 지역 랭킹은 스냅샷의 공간 행을 `location`으로 합쳐서 구한다. 지역은 새 테이블 없이 `spaces.location`에 판교·강남·하남만 쓰고, 코드의 enum으로 등록·수정 요청을 검증한다.
  6. **지표는 순매출·예약 건수·예약 슬롯 수.** 각 행이 세 지표를 모두 담고 `metric` 파라미터는 정렬 기준만 정한다. 순위(`rank`)는 저장하지 않고 조회 시 정렬해서 계산한다(공간 수가 수십 개 수준).
  7. **동점은 결정적으로 푼다.** `NET_REVENUE`: 순매출 → 예약 건수 → `space_id` 오름차순. `RESERVATION_COUNT`: 건수 → 순매출 → `space_id`. `SLOT_COUNT`: 슬롯 수 → 예약 건수 → `space_id`. 동점이어도 순위 번호는 겹치지 않고 위 순서로 매긴다(화면·API 유의사항에 명시).
  8. **기존 운영 대시보드의 "오늘 상태별 건수"만 서버 집계 API로 옮긴다.** 이 값은 실시간이다(`GET /admin/stats/status-counts`).
  9. **빠진 기간 보충과 멱등.** 서버가 00:01에 꺼져 있었으면 시작 시 빠진 기간을 찾아 채운다. 같은 기간을 다시 계산해도 `UNIQUE`로 덮어써서 결과가 중복되지 않는다.
- **이유**
  - 관리자가 가끔 보는 순위에는 실시간성보다 "그 날의 값이 어제와 오늘 다르지 않다"는 일관성이 중요하다는 요구가 있었다. 화면에서 숫자가 보는 순간마다 바뀌면 보고서·회의에서 인용하기 어렵다.
  - 현금주의로 바꾸면 확정 후에 환불이 생겨도 지난 확정값을 고칠 필요가 없고, 일간 값의 합이 주간·월간 값과 정확히 맞는다. 예약 건수는 이용 시작 시각 기준이라, 00시 시점에 해당 기간의 상태가 이미 확정되어 있어 같은 문제가 없다(취소는 시작 전에만 가능, 이후는 `COMPLETED`/`NO_SHOW`).
  - 반열린 구간으로 자르고 계산만 자정 직후에 시작하면, 23:59:59에 시작한 결제의 커밋 지연으로 인한 누락 위험을 계산 시점의 짧은 대기(00:01)로 막는다. 컷오프를 23:50으로 당기면 같은 위험이 23:49:59로 옮겨질 뿐이고, 23:50~24:00 거래가 날짜 귀속에서 흔들려 하루·주·월 합계가 어긋나므로 쓰지 않는다.
  - 메모리 캐시가 아니라 테이블에 저장하는 이유는 서버를 재시작해도 "00시에 결정된 값"이라는 표시가 사실이어야 하기 때문이다. 재시작 후 다시 계산하면 그 사이 반영된 거래가 섞인다. 지역 랭킹을 스냅샷 행에서 합쳐 지역 테이블과 별도 지역 스냅샷 테이블을 모두 만들지 않는다.

## 3. 기각한 대안과 이유

| 대안 | 장점 | 기각한 이유 |
| --- | --- | --- |
| 요청 시 실시간 계산(인덱스만 추가) | 환불이 과거 수치에 자동 반영, 정정·재집계 로직 없음, 테이블 추가 없음 | 사용자가 "대시보드에 보이는 값은 그날 24시 기준으로 고정"을 요구했다. 같은 화면을 두 번 열었을 때 값이 달라질 수 있다. 처음 제안한 안이었으나 이 요구와 충돌해 바꿨다 |
| 환불을 원 결제일 버킷에서 차감(발생주의) | 취소가 많은 날의 매출이 실제 이용과 더 가깝게 보임 | 확정값을 쓰면 확정 후 환불을 반영할 수 없어 영구히 과대 계상된다. 확정값을 고치면 "고정값"이 깨진다 |
| 서버 메모리 캐시(00시에 채움) | 테이블 추가 없음 | 재시작 시 사라지고, 다시 계산하면 확정 시점 이후 거래가 섞여 "00시 확정값" 표시가 거짓이 된다. 서버를 늘리면 인스턴스마다 값이 다를 수 있다 |
| 컷오프를 23:50으로 당김 | 직관적으로 안전해 보임 | 경계 문제를 없애지 못하고 위치만 옮긴다. 마지막 10분 거래의 날짜가 모호해져 일·주·월 합계가 어긋나고, 건수는 달력 날짜 기준이라 지표마다 기준이 갈린다 |
| `region` 테이블 신설 | 지역 확장·무결성 | 사용자가 지역을 더 늘리지 않을 계획이라 테이블 확장이 과하다고 판단했다. 대신 enum 검증으로 입력 오염을 막는다 |
| 진행 중 기간 임시 순위 표시 | 오늘의 베스트를 볼 수 있음 | 확정값과 임시값이 한 화면에 섞이고 실시간 쿼리 경로를 따로 유지해야 한다. 안내 문구로 대체한다 |
| 가동률·취소율 지표 | 공간 크기 차이를 보정 | 운영 시간·휴무 데이터가 필요하다. 1차 범위 밖이다 |
| 사전 집계 테이블에 순위 번호(`rank`)까지 저장 | 읽기가 단순 | 지표가 세 개라 순위가 세 벌이다. 공간이 수십 개라 조회 시 정렬이 더 단순하고 동점 규칙을 한 곳에 둘 수 있다 |

## 4. Trade-off

| 얻는 것 | 잃는 것(비용·위험) | 완화책 |
| --- | --- | --- |
| 하루 단위로 고정되는 숫자(보고서 인용 가능), 일·주·월 합계 일치 | 오늘·이번 주·이번 달 순위를 볼 수 없음 | 진행 중 기간에 확정 예정 시각 안내. 필요하면 재검토 조건에서 임시 순위 도입 |
| 확정 후 환불이 생겨도 과거 값을 고치지 않음 | 취소가 몰린 날 특정 공간의 일일 순매출이 그 날의 실제 이용과 어긋나 보일 수 있고, 극단적으로 음수가 될 수 있음 | 화면 유의사항에 현금주의·계산 기준을 적고, 총매출·환불액을 보조 정보로 노출할지 구현 시 검토 |
| 확정 시점에 한 번만 계산하므로 읽기가 가볍다 | 스냅샷 테이블 1개 추가, 배치 실패 시 보충 로직이 필요 | 시작 시 빠진 기간 보충, `UNIQUE` 기반 덮어쓰기(멱등), `computed_at` 표시 |
| 00:01 계산으로 자정 직전 커밋 지연 누락 방지 | 00:01 이후에 늦게 반영된 거래는 확정값에 들어가지 않음 | 한계로 문서화. 늦은 반영 감지는 3차 과제 |
| 새 지역 테이블 없이 enum 검증 | DB를 직접 수정하면 우회 가능, 지역 추가 시 배포 필요 | 등록·수정 요청 검증과 기존 데이터 확인(마이그레이션 중 값이 세 개가 아니면 중단) |
| 지역·공간 랭킹을 한 테이블에서 파생 | 지역이 바뀐 공간의 과거 지역별 순위가 달라 보일 수 있음 | 스냅샷 행에 당시 `location` 값을 함께 저장 |

## 5. 검증 계획

구현 후 "검증 결과"로 바꿔 쓴다. 필수 테스트 경계(모두 통합 테스트로, 시간은 주입된 `Clock`으로 고정):

- KST 자정 경계와 월요일 0시 경계, 월말·연말·연초, 연말·연초에 걸친 주(주 번호) 경계
- 자정을 가로지르는 예약이 이용 시작 시각의 날짜에 들어가는지, 월·연도 경계를 가로지르는 예약
- 위약금 50% 취소와 전액 환불 취소의 순매출 계산, 강제취소(위약금 없음), `NO_SHOW`(환불 없음)
- 확정 후에 생긴 환불이 지난 확정값을 바꾸지 않고 환불일의 값에 반영되는지(현금주의)
- 동점 정렬(지표별 규칙 세 가지)과 결정적 순위
- 매출·건수가 모두 0인 공간이 저장·표시에서 제외되는지, 비활성(`INACTIVE`) 공간의 과거 실적이 포함되는지
- 같은 기간을 두 번 계산해도 결과가 같은지(멱등), 서버가 꺼져 있던 기간의 보충 계산
- 빈 기간(거래 없음) 응답
- 잘못된 파라미터(없는 `metric`·`period`, 형식 오류 날짜, 현재 기간보다 미래 날짜, `limit` 범위 초과)의 400 응답, 진행 중 기간의 `PENDING` 응답, 비관리자 접근 차단(401/403)
- 운영 DB 시간대(`DB_URL`의 `serverTimezone`)가 KST와 어긋날 때 경계가 흔들리는지 확인하는 테스트
- 지역 enum 검증(공간 등록·수정), 지역별 랭킹이 공간 행의 합과 일치하는지
- 상태별 건수 API가 7개 상태를 0으로 채워 내려주는지

부하 확인: 운영과 같은 수준의 예약 데이터로 00:01 계산 쿼리 시간을 측정한다(데이터 양은 현재 미확인).

### 변경 기록 — 검증자 지적 후속 수정 (2026-10-17)

#### S1. 확정 전(00:00~00:01)의 어제 랭킹을 "실적 없음"으로 보이지 않게 한다

- **문제**: `end == today`인 기간(어제 일간, 월요일 당일의 지난주, 1일 당일의 지난달)은 `end.isAfter(today)`가 거짓이라 `PENDING`을 건너뛴다. 00:00~00:01에는 아직 확정 행이 없어서 빈 `CONFIRMED`(= "거래가 없던 기간")로 내려가 "실적 없음"으로 보인다.
- **선택**: 확정 행이 없고 현재 시각이 `기간 끝 날짜 00:01`보다 앞이면 `PENDING`을 내려준다. `confirmAt`은 기존대로 기간 끝 날짜 00:00이다(계산은 00:01에 시작). 확정 행이 이미 있으면 시각과 관계없이 `CONFIRMED`다. 테이블·컬럼을 추가하지 않는다. 사용자와 합의(2026-10-17).
- **기각한 대안**: 기간별 "확정 완료" 표식(컬럼·테이블) 도입 — 00:01 이후 확정 실패와 무거래 기간까지 정확히 구분하지만 Flyway 마이그레이션과 보충 로직 변경이 필요하고, 이번 문제(00:00~00:01)에는 과하다. 재검토 조건(아래 §6)에 이미 올려 둔 항목이라 그대로 둔다.
- **Trade-off**: 00:01 이후 확정이 실패해 행이 없는 기간은 여전히 빈 `CONFIRMED`로 보인다(보충이 다음 실행에서 채움). 이 한계는 §6에 이미 기록돼 있다.
- **후속(S2)**: 확정 서비스의 가드도 같은 기준(기간 끝 날짜 00:01)으로 맞춘다. 그래야 00:00~00:01 사이 시작 보충이 어제를 먼저 확정해 완충을 우회하는 일이 없다.

#### S2. 확정·보충 가드를 "기간 끝 날짜 00:01 이후"로 맞춤

- **문제**: 가드가 `periodEnd.isAfter(오늘)`이라 00:00:00~00:01 사이 서버 시작 보충이 방금 끝난 기간을 확정해 00:01 커밋 지연 완충을 우회할 수 있었다.
- **선택**: `SpaceRankingConfirmService.isConfirmable(periodEnd, now)`(= `now >= periodEnd 00:01`)를 확정 가드, 보충 루프, 조회의 PENDING 판정이 같은 상수(`CONFIRM_TIME`)로 공유한다. 00:01 크론은 00:01:00 이후에 실행되므로 충돌하지 않고, 보충은 00:01 전에는 그 기간을 건너뛴다(오류 로그 없음). 기존 테스트는 시계가 00:01이라 영향이 없다.
- **기각한 대안**: 보충에서만 건너뛰고 확정 서비스는 그대로 — 다른 호출 경로가 생기면 다시 우회된다. 가드를 서비스에 두는 쪽이 한곳에서 강제된다.
- **Trade-off**: 00:00~00:01에 서버가 막 떠도 어제는 1분 뒤 크론에서 확정된다(그 사이 PENDING 표시, S1).

#### S4. 대시보드 상태별 건수 기준: `start_time`이 속한 날짜 (의도한 변경)

- 상태별 건수는 "날짜에 걸치는 예약"이 아니라 `start_time`이 그 날짜인 예약으로 센다. 사용자 확인(2026-10-17): 운영상 자정을 넘기는 예약은 허용하지 않으므로 두 기준의 숫자는 같고, 예약 한 건이 정확히 하루에만 들어가며 랭킹의 예약 건수 기준과 일치한다는 이점만 남는다.
- 재검토 조건: 자정을 넘기는 예약을 허용하면 이 기준과 랭킹의 건수·슬롯 귀속을 함께 다시 본다.

### 변경 기록 — 참조 공간 누락 표시 (2026-10-27, #186)

- 스냅샷은 FK 없는 독립 집계라 확정 후 공간이 삭제되면 `space_id`만 남을 수 있다. 기존 조회는 `spaces[row.spaceId]!!`에서 NPE로 **해당 기간 전체**를 실패시켰다.
- **선택**: 누락 행을 제외하거나 뒤에서 채우지 않고 그대로 노출하되 표시 정보만 대체한다. `spaceName`은 `삭제된 공간`, `spaceStatus`는 `INACTIVE`, 원본 `spaceId`·`rank`·`previousRank`·세 지표·스냅샷 `location`·기간/상태/`computedAt`은 보존한다. 사용자 선택(2026-10-27).
- 순위는 누락 여부와 무관하게 전체 스냅샷 행을 기존 동점 규칙으로 정렬해 매기고 `limit`은 그 뒤에 적용한다. `previousRank`도 직전 기간 전체 행(누락 포함, 같은 필터) 기준이다. 지역 랭킹은 누락 행도 기존처럼 합산한다.
- **기각한 대안**: 누락 행 제외 — 확정 스냅샷의 전체 지표로 산출한 순위보다 표시 순위가 당겨지고 상위 N개가 왜곡된다. 빈 자리 채우기 — 전체 스냅샷을 정렬한 뒤 `limit`을 적용한다는 계약을 깬다. 명시적 오류 응답 — 한 공간 삭제로 기간 전체를 볼 수 없게 된다.
- 조회는 스냅샷을 쓰지 않으며 스키마·FK 변경도 없다. 존재하는 공간의 nullable 이름/상태 fallback은 기존 동작을 유지한다(#188과 분리).

- 상태별 건수 외 기존 운영 대시보드의 다른 클라이언트 집계는 그대로 남는다. 예약 목록(우선순위 정렬·8건 페이지)은 이미 날짜 필터로 선택한 날짜의 예약만 내려받는 기존 방식이다.
- `UNAVAILABLE` 판정은 근사다. 가장 이른 확정 기록보다 뒤에 있는데 계산이 실패한 기간은 빈 값의 `CONFIRMED`로 보이고, 첫 기록일 바로 전날은 실제 거래가 있어도 `UNAVAILABLE`이다. 둘 다 "빈 값 쪽"으로만 틀리고 잘못된 순위가 내려가지는 않는다.
- 거래가 없던 기간은 행이 없어 보충이 반복 계산한다. 그 사이 늦게 반영된 거래가 있으면 다음 보충 때 그 날 값이 생긴다(위 "늦게 반영된 거래" 한계의 변형).
- 지역 검증은 요청 DTO 계층에만 있다. 프런트 공간 등록·수정 폼은 판교·강남·하남 선택형으로 바꿨고, 기존 값이 다른 공간은 저장하려면 세 지역 중 하나로 바꿔야 한다.
- 랭킹 화면은 한 번에 10건만 요청한다(API는 최대 50). 스케줄러는 서버 시작 이벤트에서 보충을 동기 실행한다(31일 범위, 운영 규모 미측정).
- 구현 시 확인해야 할 미확인 사항
  - 해소: `Clock`은 `Clock.system(Asia/Seoul)` 단일 빈(`ClockConfig`)이고 원장 `created_at`은 이 Clock으로 기록된다. `RESERVATION_CHARGE`는 `-amount`로 저장되어 `−SUM(amount)`가 맞다(`CreditServiceImpl`).
  - 해소: 최초 보충 범위는 31일을 설정값(`slotkey.scheduler.space-ranking.backfill-days`)으로 구현했다. 운영 첫 배포 때 데이터 시작일을 보고 조정한다.
  - 미해소: 운영 DB `DB_URL`의 시간대 설정(`.env.example`에 값 없음)
  - 미해소: 운영 데이터 양과 실제 00:01 계산 시간(위는 합성 데이터)
- 재검토 조건
  - 관리자가 "오늘의 베스트"를 반복해서 요구하면 임시 순위 경로 추가를 검토한다.
  - 지역이 늘거나 지역별 속성(운영 시간 등)이 필요해지면 `region` 테이블 도입을 검토한다.
  - 서버가 여러 대가 되면 계산 중복 방지 락을 추가한다.
  - 계산 쿼리가 눈에 띄게 느려지면(측정값으로 판단) 집계용 보조 인덱스 또는 증분 집계를 검토한다.
  - 계산이 실패한 기간을 `UNAVAILABLE`/빈 `CONFIRMED`와 구분해야 하거나 빈 기간의 반복 계산이 문제가 되면 기간별 "확정 완료" 표식(컬럼 또는 테이블)을 도입한다.
  - 관리자가 10건을 넘는 순위를 반복해서 요구하면 화면에 `limit` 선택 또는 더 보기를 추가한다.
  - 3차에서 Kotlin 전환 시 같은 구조로 다시 구현한다(이 레포에서는 Java 유지).

## 면접·발표용 정리 (구현 후)

- **30초 설명:** 관리자 대시보드의 베스트 공간 랭킹을 "끝난 기간만, 매일 00:01에 한 번 계산해 DB에 확정값으로 저장"하는 방식으로 만들었습니다. 매출은 결제·환불·위약금을 크레딧 원장에서 발생한 날 기준으로 합산하는 현금주의라서, 확정 후에 환불이 생겨도 지난 값을 고치지 않고 환불일의 값에 반영됩니다. 서버가 꺼져 있었던 기간은 시작할 때 보충하고, 같은 기간을 다시 계산해도 UNIQUE와 덮어쓰기로 결과가 같습니다.
- **예상 질문과 답:**
  - Q. 왜 실시간 집계 대신 매일 확정값으로 했나요?
    - A. 요구가 "화면에 보이는 숫자가 그 날 24시 기준으로 고정"이었습니다. 처음엔 인덱스만 추가한 실시간 계산을 제안했는데, 같은 화면을 두 번 열면 값이 달라질 수 있어 요구와 충돌해 확정 스냅샷으로 바꿨습니다. 대신 진행 중인 기간은 순위를 보여 주지 않고 확정 예정 시각을 안내합니다.
  - Q. 환불은 어느 날짜에 반영하나요? 왜 그렇게 했나요?
    - A. 환불·위약금이 발생한 날입니다(현금주의). 원 결제일에서 차감하는 발생주의는 확정 후 환불을 반영할 수 없어 영구히 과대 계상되거나 확정값을 고쳐야 합니다. 현금주의는 일간 값의 합이 주간·월간과 정확히 맞는다는 장점이 있고, 대신 특정 날의 순매출이 음수가 될 수 있다는 점을 화면 유의사항에 적었습니다(테스트로 확인).
  - Q. 23:50에 집계를 끊지 않고 00:01에 계산한 이유는?
    - A. 23:50에 끊으면 경계 위치만 옮겨질 뿐 23:49:59 거래의 커밋 지연 위험은 그대로이고, 마지막 10분 거래의 날짜가 흔들려 일·주·월 합계가 어긋납니다. 데이터는 반열린 구간 `[00:00, 다음날 00:00)`으로 자르고 계산 시작만 00:01로 늦춰 커밋 지연을 흡수했습니다. 00:01 이후에 늦게 반영된 거래는 확정값에 들어가지 않는 한계가 있습니다.
  - Q. 서버가 00:01에 꺼져 있으면 어떻게 되나요?
    - A. 서버가 시작될 때와 매일 확정 직후에 최근 31일 안에서 확정 행이 없는 끝난 기간을 찾아 채웁니다. 이미 행이 있는 기간은 다시 계산하지 않아 확정값이 유지되고(테스트로 확인), 한 기간이 실패해도 나머지는 계속됩니다. 다만 거래가 없던 기간은 행이 없어 반복 계산되고, "계산 실패"와 구분하려면 별도 표식이 필요하다는 것을 한계로 기록했습니다.
  - Q. 규모가 커지면 어떻게 바꾸겠습니까?
    - A. 먼저 측정합니다. 합성 데이터(예약 30만 건)에서 월간 계산도 약 90ms였고 집계 인덱스를 타고 있었습니다. 느려지면 증분 집계를 검토하고, 서버가 여러 대가 되면 같은 기간 계산이 동시에 도는 것을 막는 락이 필요합니다. 지역이 늘면 `region` 테이블을 도입합니다.
- **숫자·근거 한 줄:** 백엔드 942 tests(신규 약 114) 실패 0, 프런트 75 tests 통과, 합성 30만 건에서 일간 4.6ms·주간 23ms·월간 90ms(참고치, 운영 데이터 아님). 구현·검증이 같은 세션이라 자기검증이다.
