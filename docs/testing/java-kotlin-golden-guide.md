# Java → Kotlin 골든 테스트 사용 가이드

> 적용 기준: 2026-10-22 [Issue #16 팀 합의](https://github.com/prgrms-be-devcourse/NBE12-14-3-OVENGERS/issues/16).
> 이 문서는 전환 작업에 적용할 절차다. Kotlin 전환이나 전환 후 검증의 완료 기록은 각 작업의 실행 근거로 남긴다.

Java → Kotlin 전환에서 응답 JSON을 보존하거나, 도메인 골든을 추가하거나, 골든 불일치를 조사할 때 이 문서를 따른다. **전환 전 Java 응답으로 기준 파일을 고정하고, 전환 후 같은 입력과 같은 기준 파일로 비교한다.**

## 1. 작업 입력과 범위 확인

사용자 요청·해당 Issue·작업 계획에서 아래 입력을 확인해 작업 기록에 적는다. 문서를 읽는 것만으로 Kotlin 전환이나 타 도메인 수정을 시작하지 않는다.

| 입력 | 확인할 내용 |
| --- | --- |
| 대상 | 도메인, 변경할 파일, 응답 또는 엔드포인트, 작업 담당자 |
| 단계 | Java 기준 확보 / Kotlin 전환 후 비교 / 불일치 조사 중 이번 요청의 범위 |
| 기준 소스 | 전환 전 Java 커밋과 작업 트리 변경 유무 |
| 비교 대상 | 기존 테스트·골든 경로, 대표 성공·거절 사례, 필요한 HTTP 검증 |

담당 파일은 [팀원별 상세 담당](../plans/kotlin-migration/team-guide.md)과 현재 작업의 명시적 지시를 따른다. 담당 여부가 불분명하거나 담당 밖의 수정이 필요하면 대상 파일·이유·영향 범위를 사용자에게 확인한 뒤 수정한다. 이 가이드의 역할 분담은 수정 권한을 확대하지 않는다.

**이 단계의 완료 조건:** 대상·단계·기준 소스·담당 범위가 식별되고, 각 대표 사례를 어느 테스트가 확인할지 정해져 있다.

## 2. 팀이 합의한 관리·재사용 경계

| 검증 범위 | 관리와 재사용 |
| --- | --- |
| 공통 응답 형식 (`ApiResponse`·`PageResponse`) | 합의한 공통 골든 JSON 9개를 팀 기준으로 재사용한다. 공통 응답 담당 `@Lemnoideae`가 관리한다. |
| 도메인별 응답 데이터 | 각 도메인 담당자가 전환 전 Java 응답을 확보하고 필요한 골든을 `backend/src/test/resources/golden/<domain>/`에 둔다. |
| HTTP 상태·권한·오류 매핑 | 해당 경로 담당자가 기존 컨트롤러·보안·예외 처리 테스트를 활용하고 부족한 검증을 보강한다. |

공통 골든의 위치는 `backend/src/test/resources/golden/common-response/`다. 공통 형식을 도메인마다 복제하는 대신 공통 테스트를 재사용하고, 도메인 골든은 해당 응답 데이터의 필드·값·형식을 검증한다. 실제 HTTP 응답 전체를 비교해야 하는 사례에서는 공통 형식을 포함한 전체 응답 골든도 사용할 수 있다. 같은 공통 사례만 반복하는 복제는 피한다.

공통 형식의 통과만으로 도메인 데이터의 보존을 판단하지 않는다. 직렬화 골든만으로 HTTP 상태·인증·인가·오류 매핑의 보존을 판단하지 않는다. 공통·도메인·HTTP 각각의 근거를 연결한다.

골든 파일 이름은 `<상황>-<기대결과>.json`처럼 사례를 드러내도록 정하고, 기존 도메인 명명 방식이 있으면 따른다. 예: `golden/space/detail-with-null-description.json`은 경로·이름 예시이며 파일 생성 지시가 아니다.

## 3. 전환 전 Java 기준 확보

1. **현재 소스와 기존 검증을 찾는다.** 대상 응답을 만드는 코드, 직렬화 설정, 관련 테스트와 골든을 확인한다. 응답별로 기존 검증을 재사용하고 빠진 사례만 추가한다. 사례 표에는 `상황 / 입력·사전 상태 / 골든 경로 / 테스트 / 별도 HTTP 검증`을 적는다.
2. **입력을 재현 가능하게 만든다.** ID·현재 시각·난수·외부 응답은 고정된 입력, 시계, 테스트 대역 등 기존 테스트 수단으로 통제한다. 입력 고정이 어려운 값은 변동 필드의 경로와 제외 이유를 기록하고, 해당 필드의 존재·타입·형식·의미를 별도 단언으로 검증한다. 정규화는 그 필드에만 적용한다.
3. **Java 실행에서 기대 JSON을 확보한다.** 실제 응답 생성·직렬화 경로를 실행해 결과를 검토하고 정적 JSON 파일로 저장한다. HTTP 계약을 확인하는 사례는 HTTP 테스트에서 얻은 응답을 사용한다. 운영 직렬화 설정과 다른 테스트 전용 설정으로 차이를 숨기지 않는다.
4. **정적 파일과 비교하는 테스트를 실행한다.** Java 상태에서 통과한 명령·시각·종료 코드·대상 테스트·실행/실패/오류/스킵 수를 기록한다. 기준 파일의 출처를 Java 커밋과 연결하고 미커밋 변경이 있으면 그 diff도 식별할 수 있게 보존한다.

대표 사례는 [API 계약 표](../plans/kotlin-migration/03-api-contract.md#고정할-계약)에서 대상 도메인에 해당하는 항목을 선택한다. 공통 형식의 null 생략, 중첩 null, 빈 목록·페이지, 날짜·시각, enum, 정수·소수·큰 수, 오류 응답 중 영향을 받는 경계를 사례 표에 포함한다. 요청 바인딩에 영향이 있으면 필드 누락·명시적 null·빈 문자열의 거절 응답도 확인한다. 해당하지 않는 항목은 이유를 적는다.

**이 단계의 완료 조건:** 모든 선정 사례에 Java 실행 근거와 정적 기준 파일·비교 테스트가 연결되고, 변동 필드의 별도 검증까지 통과했다. 기준 JSON이 없거나 Java에서 통과한 근거가 없으면 기준 확보를 보류한다. Java 기준만 확보한 작업은 여기서 결과를 보고하고 Kotlin 검증을 대기로 남긴다.

## 4. Kotlin 전환 후 같은 기준으로 비교

1. 요청된 전환 범위의 코드를 Kotlin으로 옮긴다. 테스트를 함께 전환할 때에도 기존 입력·기대값·단언의 의미와 기준 JSON을 유지한다([테스트 보호 장치 결정](../decisions/kotlin-test-guardrails.md)).
2. 전환 전과 같은 입력·사전 상태·직렬화 설정·변동 필드 처리로 공통 테스트와 해당 도메인 골든 테스트를 실행한다. 공유 직렬화 설정에 영향이 있으면 이를 사용하는 Java 경로도 확인한다.
3. JSON은 구조와 값으로 비교한다. 객체 키 순서·공백은 비교에서 제외하되, 필드 누락과 null, 배열 순서, 값·타입, 날짜·enum 표현은 검증한다. 정수·소수·범위가 계약에 중요하면 별도 단언으로 보강한다. 비교를 통과시키려고 배열 정렬, null 제거, 숫자의 문자열 변환 등을 추가하지 않는다.
4. 해당 경로의 HTTP 상태·권한·오류 처리 검증과 영향받는 연관 테스트를 실행한다. 빈 본문 응답은 기존 HTTP 계약에 맞춰 검증한다.
5. [공통 빌드·테스트 절차](../plans/kotlin-migration/daily/00-overview.md#빌드테스트-명령)에 따라 전체 빌드와 필요한 프론트 검사를 수행한다. 작업 중 일부 테스트만 실행한 결과와 전환 PR의 최종 검증을 구분한다.

**이 단계의 완료 조건:** 같은 기준 파일로 공통·도메인 비교가 통과하고, 관련 HTTP 검증과 적용 가능한 최종 검사 근거가 확보되었다. 필수 실행을 못 했으면 미검증 범위와 사유를 남긴다.

### 실행 명령 선택

실행 환경과 JDK·외부 의존성 조건은 위 공통 절차를 확인한다. 테스트 클래스명은 현재 소스에서 찾아 사용한다. 아래 명령의 `<테스트 클래스의 전체 이름>`은 실제 대상으로 치환한다. 각 명령은 저장소 루트에서 시작한다.

```bash
# 단일 골든 테스트 실행 예시
cd backend
./gradlew test --tests '<테스트 클래스의 전체 이름>' --rerun-tasks
```

```bash
# 전환 PR의 최종 전체 검증
cd backend
./gradlew clean build
```

XML 결과에서 대상 테스트가 실제 포함됐는지와 실패·오류·스킵 수를 확인한다. 클래스 존재나 이전 실행 보고서는 이번 통과 근거로 사용하지 않는다.

## 5. 불일치와 기준 파일 변경 처리

| 상황 | 처리 |
| --- | --- |
| 같은 입력인데 JSON이 달라짐 | 달라진 JSON 경로·기대값·실제값을 기록하고 전환 코드·직렬화·테스트 설정을 조사한다. 기존 계약을 보존하도록 수정한 뒤 같은 골든으로 재검증한다. |
| 동적 값 때문에 실행마다 달라짐 | 3단계의 입력 고정 또는 필드별 검증을 보완한다. 실제 계약 차이까지 제거하는 정규화는 적용하지 않는다. |
| 의도한 API 계약 변경이 필요함 | 변경 이유·소비자 영향·담당자 합의를 별도 작업으로 정리한다. 언어 전환과 구분하여 승인된 계약·골든·관련 테스트·명세를 함께 갱신한다. |
| Java 기준이 없거나 대상이 이미 Kotlin임 | 확인 가능한 전환 전 Java 커밋을 찾아 별도 작업 공간에서 재현한다. 기준을 재현할 수 없으면 비교 검증을 보류하고 필요한 근거를 보고한다. |
| 환경 실패·권한 부족·담당 밖 수정 필요 | 코드 문제와 분리해 기록하고 영향받는 검증을 보류한다. 승인된 범위에서 가능한 검증은 계속한다. |

기대 JSON은 테스트 실행 때마다 실제 출력으로 덮어쓰지 않는다. 자동 생성은 기준 확보를 돕는 수단이며, 검토해 확정한 정적 파일을 비교 기준으로 유지한다. 골든 변경이 필요하면 변경 전후 diff와 계약 변경 근거를 함께 검토한다.

## 6. 완료 판정과 결과 보고

Java 기준 확보와 Kotlin 전환 후 검증의 상태를 각각 기록한다. Issue #16 종료는 관리·재사용 합의의 완료이며 개별 도메인의 전환·검증 완료 근거로 사용하지 않는다.

결과에는 아래 항목을 남긴다. 팀 공유 결과는 [테스트 결과](test-results.md) 또는 해당 작업 PR에서 확인할 수 있게 연결한다.

```text
대상·요청 단계·담당 범위:
Java 기준: 커밋 / 미커밋 diff 식별 / 기준 확보 실행 근거
Kotlin 비교: 커밋 / 작업 트리 상태 / 완료·대기·보류
사례별 대응: 상황 / 골든 경로 / 테스트 / 별도 HTTP 검증
변동 필드: 경로 / 통제·별도 단언 / 제외 이유
실행 근거: 시각 / 환경 / 명령 / 종료 코드 / 실행·실패·오류·스킵 수
최종 검사: 전체 빌드 / 필요한 프론트 검사 / 미실행 사유
기준 JSON 변경: 없음 또는 별도 계약 변경 근거
발견 문제·미검증 범위·다음 조치:
판정: Java 기준 확보 상태 / Kotlin 비교 상태 / 이번 요청의 완료 여부
```

전환 PR은 빌드 성공·목적대로 동작·검토 범위에서 중 이상 문제 없음을 모두 확인해야 완료다([공통 완료 기준](../plans/kotlin-migration/README.md#완료-기준)). 개별 클래스·파일 목록과 실행 결과는 작업 시점의 소스·보고서에서 확인한다.
